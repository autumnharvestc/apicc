# 服务端 BIGINT 主键化 + 成员按用户名搜索 设计

日期：2026-09-09
状态：口径已获用户确认（2026-09-09 缺陷反馈），规格终审中
关联：org-rbac 设计（2026-09-08）§2/§3/§4；两批均未实现

## 缺陷一：主键禁用 UUID，全表切 64 位整数

用户指令（2026-09-09）：「数据库表的主键怎么可以用 UUID，要用 64 位的整数型……所有表都要检查」。

### 现状盘点（已核对 schema.sql 与两侧源码）

8 张表，两类：

| 表 | 现主键 | 判定 |
|---|---|---|
| users / workspaces / groups / projects | `VARCHAR(36)` UUID（`UUID.randomUUID()` 文本） | **改造对象**：实体主键切 BIGINT IDENTITY |
| tokens / memberships / project_acl / file_versions | 自然键（token_hash SHA-256、复合键） | 主键形态保留；**键列中的实体 id 列同步切 BIGINT** |

外键列全量跟随：`tokens.user_id`、`workspaces.created_by`、`memberships(workspace_id,user_id)`、`project_acl(workspace_id,project_id,user_id)`、`file_versions(workspace_id,updated_by)`、`projects(workspace_id,group_id)`。`project_acl.project_id`（现 VARCHAR(64)）跟随项目实体 id 切 BIGINT。

### 口径

1. **DDL**：实体主键 `BIGINT GENERATED BY DEFAULT AS IDENTITY`（H2 与 PG 同语法，守住 schema.sql 可移植约束）。**取 BY DEFAULT 而非 ALWAYS**：默认自增，同时允许显式 id 插入——为可插拔 id 策略留通道（见口径 2）。代码侧删除全部 `UUID.randomUUID()` 生成点（AdminBootstrap / DefaultWorkspaceSeeder / 各 Service / ContentService）。
2. **ID 生成策略可插拔（用户裁定 2026-09-09）**：策略接口（`IdGeneration`：`boolean appAssigned()` + `long nextId()`）经配置项选择（`apicc.id-generation`，默认 `identity`）。
   - 默认 `identity`＝数据库自增：INSERT 不带 id 列，经 KeyHolder 取回生成键。
   - 外部策略（雪花等，部署方按需接入）：插入前 `nextId()` 预生成、INSERT 显式带 id（BY DEFAULT IDENTITY 允许显式值）。本轮只交付接口 + 默认实现 + 装配点，雪花本体与其 workerId 配置留待按需实现；仓储层插入路径按 `appAssigned()` 分支，两种形态共用同一 DDL。
3. **语义字段零改动（用户明确要求）**：换型仅限「实体身份 id 及其外键引用」九类列；内容性字段类型一律不动——`tokens.token_hash`（SHA-256 自然主键，本就不是 UUID）、`file_versions.path / content_hash / version`（version 本就是 BIGINT）、`users.username / password_hash / display_name / role / disabled`、各时间戳列、`groups.is_default` 等。`file_versions` 的 (workspace_id, path) 自然复合主键、`memberships`/`project_acl` 复合键结构保留，仅其中 id 引用列换 BIGINT。
4. **Java 内部类型**：实体 id 全链 `String → Long`（Record、Repo、Service、PermissionService、AuthFilter 属性、守卫判据）。编译器兜底扫尾。
5. **对外 JSON 形态＝字符串化数字（裁定 B，终审可改）**：View/DTO 的 id 字段类型保持 `String`，组装处 `String.valueOf(...)`（如 `"1"`、`"42"`）。理由：桌面契约（`apps/desktop/src/shared/online/contract.ts`）全部 id 为 `z.string()` 且无 uuid() 校验——**契约与桌面测试夹具零改动**（构建约束教训：zod schema 改动波及全部夹具）；URL/path 中的 id 段形态不变。用户诉求（存储层整数主键、界面不暴露手输 id）均不受影响。
6. **path 首段 pattern 两侧同步**：服务端 `ContentPaths.PROJECT_ID_PATTERN` 与桌面 `session.ts PROJECT_ID_PATTERN` 从 UUID 正则改 `^\d+$`（纯数字）；「裸 id 单段不归属项目」的占位防碰撞逻辑保留；错误文案「（UUID）」→「（数字 id）」。本地（非在线）内容树不经此 pattern，不受影响。
7. **无迁移**：沿用未发布阶段口径（schema.sql 头注），旧库删 `server-data`/容器卷重开。
8. **测试口径**：服务端契约测试断言 id 形态 `^\d+$`；启动冒烟含 seeder/引导建号；id 策略装配默认 `identity` 回归，另以假 `appAssigned` 策略单测验证显式 id 插入通道（BY DEFAULT 语义）；桌面端重点回归在线树构建（session.ts pattern）与 mapping 换算（`parseWorkspacePath`）。桌面 mock 替身（memory.ts）id 形态已是字符串，不动。

## 缺陷二：工作区加成员改「用户名搜索下拉」

用户指令（2026-09-09）：「需要按用户名匹配搜索在下拉框中选择，让用户直接输入 ID（对用户不可见的内容）这种错误以后不准再犯」。**先例级教训：内部 id 一律不得要求用户手输。**

### 服务端

- 新端点 `GET /api/v1/workspaces/{id}/member-candidates?q=<关键字>&limit=10`：
  - 权限与添加成员同档（工作区 ADMIN+，经 WorkspaceGuard）；
  - 按 `username` / `display_name` 大小写不敏感包含匹配（`LOWER(...) LIKE %q%`，q 必填非空、trim 后 ≤32 字符）；
  - 排除已是本工作区成员的用户；按 username 升序，默认 LIMIT 10；
  - 返回 `[{id, username, displayName}]`（id 同缺陷一口径=字符串化数字）。
- 现有 `PUT /api/v1/workspaces/{id}/members/{userId}` 契约不动（选中候选项后前端持其 id 调用）。

### 桌面端

- 契约：`shared/online/contract.ts` 增候选行 schema（复用 OnlineUserSchema 形状）+ client 增 `memberCandidates` 方法（主进程 online session 透传）。
- MembersView：userId 直填输入框替换为远程搜索下拉——输入 ≥1 字符即 debounce（约 300ms）拉候选，选项展示 `username（displayName）`，选中后界面仅回显用户名，id 不见即用；维持既有角色选择与提交链路。
- mock 替身（memory.ts）同步补候选行为（按夹具用户过滤），供组件测试。

### 测试口径

- 服务端 MockMvc：命中/排除已有成员/limit 截断/无权 403/q 空 400。
- 桌面组件：搜索下拉出候选、选中回填、提交载荷携带所选 id。
