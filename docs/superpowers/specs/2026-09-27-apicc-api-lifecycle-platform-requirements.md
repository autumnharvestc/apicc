> 状态：已批准进入规划

- `2026-09-27-apicc-core-capability-baseline-design.md`：执行、工作流、压测和报告可信度；
- `2026-09-27-apicc-plugin-api-and-script-security-design.md`：插件 API、脚本信任、密钥、网络和服务端任务安全；
- 本文：完整 API 生命周期能力、模块边界、本地/在线承诺和阶段依赖。

出现冲突时，日期相同的文档按以下顺序解释：

1. 用户已确认的明确决策；
2. 本文的产品范围与边界；

## 2. 产品定位

apicc 是本地优先、数据可控、Git 友好的 API 设计与测试开发平台。它以 apicc 结构化契约为唯一事实来源，把接口资产、设计、调试、文档、Mock、功能测试、场景编排、开发阶段压测和报告组织为连续工作流，并通过可选服务端增强协作、共享和长期调度。

核心价值：

1. **本地完整**：不登录、不购买在线服务也能完成设计、调试、Mock、测试、编排、压测、报告和导出；
2. **契约驱动**：同一份结构化契约驱动编辑、执行、文档、Mock、测试生成和导入导出；
3. **结果可信**：不同执行入口具有一致且可解释的请求、脚本、断言和错误语义；
4. **协作可选**：服务端增强团队能力，但不削弱本地能力或锁定本地数据；
5. **扩展受控**：插件公开 API 可演进，脚本只作为受控测试辅助能力。

## 3. 已确认的产品裁定

### 3.1 本地与在线边界

- 本地版保证接口设计、调试、Mock、测试、编排、压测、报告和导出完整可用；
- 在线/自托管服务提供成员、权限、共享、审计、服务端任务和长期调度等增强能力；
- 本地资产可独立存在，不因退出登录、服务端不可用或团队订阅变化而失去核心能力；
- 服务端任务由服务端独立执行，不受桌面关闭影响；
- 本地任务依赖本地进程，不自动迁移或接管为服务端任务。

### 3.2 数据事实来源

- apicc 结构化契约是唯一事实来源；
- OpenAPI、Postman、cURL 和其他格式用于导入、导出与交换；
- 外部规范同步必须进入显式差异和冲突流程，不能静默覆盖 apicc 契约；
- 文档、Mock、用例建议和代码片段均从结构化契约派生。

### 3.3 兼容策略

- 产品尚未发布，新结构化契约无需兼容旧 `ApiDefinition`；
- 不为旧工作区实现迁移器，不让历史试验模型限制新契约设计；
- 新契约首次落地即携带明确格式版本；
- 首次正式格式落地后的兼容与迁移必须有版本、诊断和自动化测试。

### 3.4 压测定位

- 当前目标是可信的开发阶段单机压测和业务场景压测；
- 必须报告负载生成器限制，不能把客户端瓶颈解释成服务端性能；
- 分布式负载平台、跨节点协调和大规模性能基础设施留作未来扩展；
- 核心模型应保留未来扩展边界，但当前需求和 UI 不宣称分布式能力。

### 3.5 插件与脚本

- 插件采用独立 `@apicc/plugin-sdk`、`apiVersion`、插件版本和宿主版本范围；
- V1 插件是用户显式安装的本地受信代码，项目不能自动携带并执行插件；
- 脚本支持标准 JavaScript 与常用 Postman `pm` API 子集，但不兼容 Node/npm；
- 共享和服务端脚本不能读取密钥原文；
- 脚本无原生文件、进程、系统环境和任意网络能力；
- 完整安全要求引用专项安全规格。

## 5. 产品信息架构

项目至少包含以下一等资产：

- 接口与接口目录；
- 数据模型与可复用组件；
- Markdown/项目说明文档；
- 环境、普通变量与密钥引用；
- 单接口测试用例；
- 场景与工作流；
- 测试套件；
- 测试数据；
- Mock 配置；
- 请求历史与运行历史；
- 报告；
- 共享脚本与声明式操作库；
- 服务端任务定义与不可变执行快照。

资产树、搜索、过滤、最近访问和多标签工作区必须能覆盖上述主要资产。接口管理、自动化测试、Mock 和报告可以采用不同视图，但不得形成相互复制的数据孤岛。

## 6. 结构化接口契约（CONTRACT）

结构化契约是后续大多数能力的共同前置条件。

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| CONTRACT-001 | P0 | 接口包含协议、方法、基础地址、路径、名称、说明、标签、版本和生命周期状态 | 契约可完整往返存储，编辑后无字段丢失 |
| CONTRACT-002 | P0 | 独立描述 Path、Query、Header、Cookie 参数 | 每个参数支持类型、必填、默认值、示例、枚举、说明和启用状态 |
| CONTRACT-003 | P0 | 支持 none、JSON、XML、Text、GraphQL、urlencoded、multipart 和 Binary 请求体 | multipart 文本与文件字段可设计、保存、发送和导出 |
| CONTRACT-004 | P0 | 支持多个响应状态、响应头、内容类型、Schema 和示例 | 同一接口可描述并预览成功与错误响应 |
| CONTRACT-005 | P0 | 支持对象、数组、标量、枚举、必填、嵌套、组合和模型引用 | 请求/响应引用统一模型，引用错误在执行前诊断 |
| CONTRACT-006 | P1 | 支持可复用参数、认证、安全方案、响应和示例组件 | 多接口引用同一组件，修改后引用方可追踪变化 |
| CONTRACT-007 | P0 | 契约同时驱动调试、文档、Mock、测试、代码片段与导入导出 | 变更契约后各消费面使用同一版本，无重复录入 |
| CONTRACT-008 | P0 | 新契约从首次落地起显式版本化 | 不兼容版本明确拒绝并给出诊断，不静默丢字段 |

认证首批至少覆盖 None、Bearer、Basic 和 API Key；OAuth 2.0、自定义 CA 与 mTLS 按真实使用场景进入 P1。认证配置中的密钥只保存引用。

## 8. 请求调试（DEBUG）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| DEBUG-001 | P0 | 编辑 Query、Path、Header、Cookie、认证、Body 和请求设置 | Path 从模板识别，所有部分均能按契约校验 |
| DEBUG-002 | P0 | 支持环境、变量、Cookie jar、代理、重定向和超时 | 最终请求能追溯每个有效值的来源 |
| DEBUG-003 | P0 | multipart 支持文本与文件混合上传 | 标准测试服务收到正确字段、文件名、类型和内容 |
| DEBUG-004 | P0 | 展示 Body、Headers、Cookies、控制台、断言和实际请求 | 实际请求反映变量、脚本、认证和全局参数处理后的结果 |
| DEBUG-005 | P1 | Body 支持 Pretty、Raw、Preview、复制、下载、搜索和编码选择 | JSON/XML/文本/二进制使用相应查看方式，失败有诊断 |
| DEBUG-006 | P0 | 逐次调试写入可配置的本地请求历史 | 可搜索、按时间筛选、重放、恢复编辑和删除 |
| DEBUG-007 | P0 | 调试请求可保存为单接口用例 | 保存后保留有效请求覆盖、环境引用和断言草稿 |

历史、实际请求和日志必须遵守密钥与敏感字段遮罩策略。本地历史默认保存遮罩后的完整报文，并支持保留天数、数量上限或关闭。

|---|---|---|---|
| MOCK-001 | P1 | 本地根据方法、路径和契约启动 Mock 服务 | 不登录服务端即可获得固定且可复现的响应 |
| MOCK-002 | P1 | 支持选择响应状态、示例、Schema 生成、响应头和延时 | 配置变化立即反映，报告命中的配置来源 |

| MOCK-004 | P2 | 支持受控脚本化 Mock 规则 | 脚本遵守统一脚本安全和密钥策略 |

## 13. 开发阶段压测（STRESS）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|

| STRESS-106 | P1 | 支持恒定并发、恒定到达率和阶段升压 | 生成器未饱和时实际到达率满足误差目标 |
| STRESS-107 | P1 | 报告吞吐、成功率、错误、延迟分位数、时间序列和节点指标 | 指标标明采样窗口、配置和数据完整性 |
| STRESS-108 | P1 | 压测脚本使用预编译隔离 Worker 池和采样日志 | 不按请求创建进程，不保存无限成功日志 |
| STRESS-109 | P1 | 支持场景压测和虚拟用户生命周期 | `setup/vuSetup/iteration/teardown` 行为和指标可验证 |
| STRESS-110 | P0 | 对非本地或首次目标提供显式确认与目标策略 | 安全判断不依赖用户自定义环境名称或标签 |
| STRESS-111 | P0 | 报告负载生成器 CPU、内存、队列与饱和状态 | 生成器饱和时报告不把客户端瓶颈解释为服务端性能 |

本需求基线不包含分布式发压和跨节点状态同步。

## 15. 项目资源、任务与协作（COLLAB）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| COLLAB-001 | P1 | 集中管理常用字段、环境、数据集、共享脚本和操作库 | 资产引用稳定、可查找、可诊断缺失 |
| COLLAB-002 | P2 | 支持项目成员、邀请、角色和最小权限 | 分享、密钥、脚本和任务权限可独立控制 |
| COLLAB-003 | P2 | 保留编辑共享脚本、管理密钥绑定、管理服务端任务三个权限点 | 项目所有者可同时拥有全部权限，不强制职责分离 |
| COLLAB-004 | P2 | 服务端任务使用不可变执行快照 | 项目更新不静默改变任务，报告记录快照 ID |
| COLLAB-005 | P2 | 服务端定时运行套件或场景并产生通知 | 桌面关闭不影响服务端任务；本地任务不自动转移 |
| COLLAB-006 | P2 | 在线提供共享历史和受控文档分享 | 权限、撤销、保留期和敏感信息策略可配置 |
| COLLAB-007 | P2 | 数据库、Git 和自定义函数以受控资源或插件提供 | 不通过测试脚本开放任意系统权限 |
| COLLAB-008 | P2 | 记录成员、脚本、密钥引用、任务和同步审计 | 审计不保存密钥值，能关联操作者和执行快照 |

平台不基于“生产”“测试”等用户自定义环境标签实施特殊权限或双人审批。

## 16. 插件与脚本（EXT/SEC）

以下要求由插件与脚本安全专项规格详细定义，本文固定其产品级门槛：

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| EXT-101 | P1 | 插件使用独立 SDK 和显式 API 版本 | 不兼容插件在执行 `setup()` 前被拒绝 |
| EXT-102 | P1 | 贡献使用命名空间 ID，重复注册拒绝 | 不发生静默覆盖或部分注册 |
| EXT-103 | P1 | 项目不能自动安装或执行插件 | 打开恶意夹具不产生代码执行 |
| SEC-101 | P0 | 共享脚本默认按单脚本、单版本授权 | 内容或权限变化使对应授权失效 |
| SEC-102 | P1 | 用户可选择信任整个项目，但权限扩张重新授权 | 新网络目标、密钥或执行范围不能静默获得权限 |
| SEC-103 | P0 | 脚本无原生文件、进程、系统环境和 npm 能力 | 越权夹具被拒绝并产生稳定错误类型 |
| SEC-104 | P0 | 额外网络只通过白名单 `pm.sendRequest()` | 重定向和名称解析不能绕过目标限制 |
| SEC-105 | P0 | 共享和服务端脚本只通过句柄使用密钥 | 日志、异常、编码和网络夹具无法得到密钥原文 |
| SEC-106 | P0 | 密钥不进入历史、日志、报告、分享、导出和 AI 上下文 | 自动化扫描所有产物无密钥原文 |
| SEC-107 | P1 | 前置、后置和 finally 具有确定顺序与失败语义 | 多层操作轨迹和组合失败测试符合专项规格 |
| SEC-108 | P1 | 功能与压测共用安全模型、使用不同资源配置 | 压测不放宽权限，脚本机制不污染 HTTP 指标 |

| 文档与代码片段 | 是 | 受控分享链接 |

## 18. 非功能性要求

### 18.1 可用性

- 日常闭环“设计/导入 → 调试 → 查看实际请求与响应 → 保存为用例 → 运行 → 报告”不应要求切换多个互不关联的数据副本；
- 错误提示必须说明失败阶段、对象、稳定错误码和可行修复方向；
- 未实现能力不得显示为可用入口，实验能力必须明确标记。

### 18.2 性能与规模

- 单项目至少支持 10,000 个接口资产的索引、搜索和增量保存；
- 工作流至少支持 500 个节点的加载和校验；
- 单机压测支持 1,000 并发配置表达，实际吞吐由生成器资源报告说明；
- 长时间压测使用有界内存聚合，不按样本数量线性增长；
- 请求、响应、日志和产物均有可配置软限制和不可绕过的宿主硬限制。

### 18.3 可移植与工程基线

- Windows 是首要正式支持平台；
- Node.js 基线保持 `22.19.0` 或项目后续明确升级版本；
- 服务端以 JDK 21 为构建和运行基线，`JAVA_HOME` 指向 JDK 根目录而不是 `bin`；
- 本地核心资产保持文本化、可进入 Git 并可由 CLI 运行；
- 桌面、CLI 和服务端共享契约、错误和报告 DTO 的契约测试。

### 18.4 安全与隐私

- 密钥与项目文件分离；
- 脱敏在日志、事件广播、历史和报告持久化之前完成；
- 共享与服务端执行遵守最小权限、网络白名单、资源上限和审计；
- 完整报文的本地与服务端留存采用不同默认策略；
- 安全机制不依赖用户可任意命名、复制或删除的环境标签。

## 20. 优先级与依赖顺序

### P0：基础可信与高频闭环

1. 执行可信度与压测可信度基线；
2. 结构化接口契约、数据模型与首次格式版本；
3. Path/Cookie、multipart、实际请求和完整响应；
4. 本地请求历史、重放和保存为用例；
5. 脚本密钥、脱敏和禁止系统能力的 P0 安全边界。

### P1：完整本地产品

1. 结构化设计器、实时文档、代码片段和本地导出；
2. 本地 Mock；
3. 测试套件、集中数据、丰富断言和增强报告；
4. 强场景编排与场景压测；
5. 插件 SDK V1 与受限脚本运行时；
6. OpenAPI/Postman/cURL 导入及 OpenAPI/文档导出。

### P2：在线协作与长尾兼容

1. 服务端任务、不可变快照和通知；
2. 共享历史、文档分享和共享 Mock；
3. URL/Git 规范同步与冲突治理；
4. 长尾导入导出插件；
5. 团队权限、资源和审计深化。

依赖约束：

- 执行可信度先于场景压测和高级报告；
- 结构化契约先于设计器、文档、Mock、代码片段和高保真导出；
- 密钥与脚本安全基础先于共享脚本和服务端任务；
- 插件 SDK DTO 依赖结构化契约的稳定公开视图；
- 本地核心达到完整门槛后，再增加不影响本地能力的在线增强。

## 21. 发布门槛

在宣称 apicc 达到“好用的 API 测试开发平台”前，至少满足：

1. 本地无需登录即可完成结构化设计、调试、Mock、用例、场景、压测、报告和导出；
2. 同一用例在单次运行、批量运行、工作流和单迭代压测中的有效请求与断言语义一致；
3. 契约修改能同步驱动文档、Mock、测试和 OpenAPI 导出；
4. multipart 文件、Cookie、实际请求、完整响应和请求历史形成日常调试闭环；
5. 工作流能表达条件、循环、并行、重试、错误路由和 finally，并提供可诊断轨迹；
6. 压测报告区分服务错误、脚本、断言和生成器瓶颈，指标口径可解释；
7. 共享和服务端脚本无法直接访问系统资源或读取密钥原文；
8. 密钥不进入项目、日志、报告、分享、导出和 AI 上下文；
9. OpenAPI 3、Postman 2.1 和 cURL 导入有保真与失败诊断；
10. Windows 本地完整验证通过，服务端在 JDK 21 基线上构建与运行。

## 22. 明确不纳入当前主线

- 订单、套餐和商业计费后台；
- 公共 API 市场/API Hub 运营体系；
- 与 API 开发测试无关的完整组织门户；
- 一次性支持截图中的全部导入格式和全部代码语言；
- 与 Git 重叠但缺少清晰合并语义的内部项目分支系统；
- 脚本原生文件、进程、系统环境、Node/npm 权限；
- 分布式性能平台和跨节点压测状态同步；
- 以环境名称或“生产”标签作为真实安全边界；
- 在线能力限制或阉割本地核心功能。
