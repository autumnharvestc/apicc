# apicc M1「本地核心」设计规格

- 日期：2026-09-01
- 状态：已确认设计，待用户最终审查
- 范围：M1 里程碑（本地单机版）；本文档同时记录整体定位与 M1–M7 路线图
- 参考原始需求：`local/原始需求.md`（不入库）

## 1. 背景与定位

apicc 是一个开源（MIT）的、**本地优先**的 API 全生命周期平台：接口定义、调试、测试、压测、在线协作、AI 设计导出。对标 Postman（调试/集合）+ JMeter（测试编排/压测）+ YApi（接口管理）的一体化体验。

**一句话定位**：本地优先、一切皆插件、定义驱动 AI 开发的开源 API 平台。

**目标用户**：
- 第一公民：个人开发者 / 测试工程师——下载即用，免登录，数据以文本文件存于本地、可 Git 管理
- 第二公民：研发团队——可选开启在线模式获得协作、权限、分布式压测（M3 起）

**四条差异化立场**：
1. 本地模式功能完备，不设登录墙（对比 Postman/Apifox 强制账号体系）
2. API 定义即代码资产：纯文本 + Git 优先，可 diff、可评审、可离线
3. 接口详细设计可导出为 agent 可消费的格式——人写设计、agent 实现代码
4. 一切皆插件：协议、认证器、断言、脚本引擎、报告、导入器、存储适配器均为扩展点

**M1 成功标准**：一位未接触过本平台的测试工程师，30 分钟内完成「导入 Swagger → 调试接口 → 编写测试用例 → 运行集合 → 查看报告」全流程；此后日常 API 调试工作不再需要 Postman。

## 2. 已确认的关键决策

| # | 决策 | 结论 |
|---|------|------|
| D1 | 首个里程碑 | M1 本地核心先行；架构预留扩展性与可移植性，遵循「一切皆插件」，钩子设计优先 |
| D2 | 测试定位 | 功能测试 + 压测都要；执行引擎从设计起支持并发采样、指标汇聚、分布式扩展 |
| D3 | Mock 能力 | 作为独立插件在 M2 后实现；M1 在数据模型预留 |
| D4 | 脚本语言 | JavaScript 为一等公民；脚本引擎抽象为 `ScriptEngine` 扩展点，可插拔其他语言 |
| D5 | 接口详细设计 | M1 即建立设计实体（结构化 + 自由文本）并提供 agent 友好导出；AI 智能生成在 M6 |
| D6 | 本地存储形态 | 文本文件 + Git 优先；SQLite 仅作可重建的索引缓存 |
| D7 | 整体架构 | 方案 A：平台无关 TypeScript 核心包 + Electron/CLI 宿主；在线模式复用同一 core，重压测 worker 为可替换进程插件 |

## 3. M1 范围

### 3.1 包含

| 模块 | 需求 |
|------|------|
| 工作区 | 本地目录即工作区；数据为 Git 友好的 YAML/JSON 文本；`.apicc/` SQLite 索引可随时删除重建 |
| 组织结构 | 分组 → 项目 → 集合 → 文件夹 → 接口 五级；测试阶段即环境（dev/sit/press…），隶属项目统一管理 |
| 环境派生 | 新环境可由已有环境派生（`extends`）：继承变量与用例可见性，子环境可覆盖变量 |
| 用例与环境 | 接口定义全局唯一、各环境一致；测试用例分「基座用例」（全环境共享）与「环境用例」（`.<env>` 后缀，仅该环境生效/覆盖） |
| 变量体系 | 全局 / 项目 / 环境 / 集合四级静态变量 + 内置动态变量（`{{$timestamp}}`、`{{$uuid}}` 等）+ 脚本运行时变量；优先级与循环引用检测见 §7.3 |
| REST 调试 | 全 HTTP 方法、query/header、body（JSON / form / xml / raw / graphql）、超时与代理配置 |
| 请求认证 | Bearer / Basic / ApiKey 内置；通过 `AuthProvider` 扩展点后续叠加 OAuth2 等 |
| 测试用例 | 一接口多用例；断言覆盖状态码、响应头、JSONPath 取值、响应时间；前置脚本（改请求、取变量）、后置脚本（断言、提取变量） |
| 数据驱动 | 单请求模板用例遍历：CSV/JSON 数据源逐行展开执行 |
| 集合运行 | 集合/文件夹顺序执行；运行历史落盘；测试报告（用例通过率、断言详情、耗时）可导出 HTML / JUnit |
| 接口详细设计 | 接口挂 `design.md`（结构化 schema 段 + 自由文本）；可导出含定义、schema、校验规则、错误码、示例的 agent 友好 Markdown |
| 导入 | Postman collection v2.1、OpenAPI/Swagger 2.0 与 3.0；导入前预览差异、不静默覆盖 |
| 插件底座 | §5 定义的 7 个扩展点 + 事件总线；所有内置功能以普通插件形态实现 |
| CLI | `apicc run <集合> --env <环境> --reporters html,junit`，可用于 CI |

### 3.2 不包含（后续里程碑）

DAG 工作流与编排（M2）、压测并发模型（M2）、Mock 服务（M2 后插件）、在线协作/平台认证/权限（M3）、管理后台（M4）、gRPC/WebSocket/MQTT/SOAP 协议（M5）、AI 生成用例（M6）、插件市场与 UI 扩展点（M7）、审批式接口版本生效流程（M3+ 评估）。

## 4. 总体架构

```
┌────────────────────────────────────────────┐
│ 宿主层                                      │
│  ├─ Electron App（M1 主宿主，Vue 3 渲染层）  │
│  └─ CLI（apicc 命令，复用同一 core）         │
├────────────────────────────────────────────┤
│ @apicc/core（平台无关 TypeScript 核心包）    │
│  ├─ 域模型：接口/集合/环境/用例/详细设计      │
│  ├─ 工作区管理器：加载、保存、校验、索引       │
│  ├─ 执行引擎 Runner：遍历→脚本→请求→断言      │
│  ├─ 事件总线：所有钩子的载体                  │
│  └─ 插件注册中心：发现、注册、依赖解析         │
├────────────────────────────────────────────┤
│ 内置插件（同仓库交付，但只依赖公开插件接口）   │
│  http-client / basic-auth / js-script-      │
│  engine / html-reporter / junit-reporter /  │
│  postman-importer / openapi-importer        │
├────────────────────────────────────────────┤
│ 存储：工作区目录（YAML/JSON 文本，Git 友好）  │
│      + .apicc/ SQLite 索引（缓存，可重建）    │
└────────────────────────────────────────────┘
```

要点：
- core 不依赖 Electron 与 Node 专有 API 的能力（HTTP 执行、文件读写经适配层注入），保证可运行于 Electron 主进程、Node CLI，以及 M3 的服务端 Node 进程
- SQLite 索引仅为查询加速，任何时刻可由文本文件全量重建；两者以文件 mtime + 内容哈希对账

## 5. 插件模型

### 5.1 扩展点（M1 定义 7 个）

| 扩展点 | 接口职责 | 后续叠加示例 |
|--------|----------|--------------|
| `ProtocolClient` | `canHandle(schema)` + `execute(request) → Response` | gRPC/WS/MQTT/SOAP（M5） |
| `AuthProvider` | 为请求注入凭证 | OAuth2 |
| `AssertOperator` | 断言操作符（eq/contains/jsonPath/lt/gt/…） | 自定义断言 |
| `ScriptEngine` | `run(code, ctx)`，默认实现 JS 沙箱 | Groovy/Python 引擎 |
| `Reporter` | 消费执行结果事件流渲染报告 | 压测 TPS 报告（M2） |
| `Importer` | `detect(file)` + `parse(file) → 域对象` | SoapUI/Insomnia 导入 |
| `StorageAdapter` | 工作区读写 | M3 在线数据库实现同一接口——可移植性的关键钩子 |

### 5.2 事件总线（钩子）

执行生命周期事件：`beforeRun / beforeCase / beforeRequest / afterResponse / afterCase / afterRun`。
插件与用户前后置脚本挂同一条总线；M3 服务端钩子沿用同一事件契约。事件携带只读快照 + 受控变更通道，避免插件间隐式耦合。

### 5.3 插件契约测试

每个扩展点附带契约测试套件；内置插件必须全部通过，未来第三方插件以同一套件验收。

## 6. 数据模型与工作区文件结构

```
my-workspace/                      ← 一个 Git 仓库
├── apicc.workspace.yaml           ← 工作区元信息 + 全局变量
└── groups/ecommerce/projects/order-service/
    ├── project.yaml               ← 项目变量、环境定义
    ├── environments/
    │   ├── dev.yaml               ← 变量集；可声明 extends: base 派生
    │   └── sit.yaml
    └── collections/order-api/
        ├── collection.yaml        ← 集合变量、集合级前后置脚本
        └── apis/create-order/
            ├── api.yaml           ← 接口定义（全局唯一，不随环境变）
            ├── design.md          ← 接口详细设计（agent 可消费）
            └── cases/
                ├── ok.yaml        ← 基座用例（所有环境共享）
                └── ok.sit.yaml    ← sit 环境特有/覆盖用例
```

规则：
- **稳定标识**：每个对象携带 ULID；对象间引用一律用 ID，重命名/移动目录不破坏引用；文件路径仅负责人工可读
- **版本**：`api.yaml` 含语义化 `version` 与 `deprecated` 元数据；变更历史由 Git 承载；审批式「版本生效」流程推迟到 M3+ 评估
- **校验**：所有 YAML 受 zod schema 约束，未知字段报错（防拼写漂移）
- **Mock 预留**（D3）：`api.yaml` 的响应示例结构即为后续 Mock 规则的数据来源，M1 不实现 Mock 引擎

## 7. 关键流程

### 7.1 调试流
UI 编辑请求 → 前置脚本（可修改请求/读取变量）→ `ProtocolClient` 发送 → 后置脚本（断言/提取变量）→ 展示响应与断言结果。

### 7.2 集合运行流
选定集合 + 环境 → Runner 顺序遍历用例；数据驱动用例按数据源逐行展开 → 每条用例走完整调试流 → 结果以事件流写出 → `Reporter` 渲染，原始结果 JSON 先行落盘至 `runs/`。

### 7.3 变量解析
优先级（高→低）：脚本运行时变量 → 环境变量 → 集合变量 → 项目变量 → 全局变量 → 内置动态变量。解析期检测循环引用，报错并输出引用链。

### 7.4 导入流
选文件 → `Importer.detect` 识别格式 → 解析映射为域对象 → 预览差异（新增/更新/冲突计数）→ 用户确认后写入；不静默覆盖已有对象。

### 7.5 Agent 导出流
选中接口/集合 → 渲染内置模板 → 输出 Markdown（接口定义 + design.md + 数据模型 schema + 校验规则 + 错误码 + 示例）。

## 8. 错误处理

- **工作区加载**：逐文件 schema 校验；坏文件隔离标记、不阻塞其余加载，UI 给出修复指引
- **脚本异常**：JS 沙箱不暴露 `fs`/`net`，仅提供注入的 `pm.*` 上下文 API；脚本执行超时默认 3s；单用例脚本失败默认不中断集合，可配置 fail-fast
- **网络错误**：连接超时默认 10s、总超时默认 30s，均可配置；错误分类展示（DNS / 连接拒绝 / 超时 / TLS）
- **并发写**：进程内写队列串行化；Git 合并冲突由用户在 Git 层解决，加载时 schema 校验兜底
- **报告失败**：报告渲染异常不影响执行——原始结果 JSON 已先行落盘

## 9. 测试策略

- core 单元测试（vitest）：域模型、变量解析、断言操作符、导入器（使用真实 Postman/OpenAPI 样例文件）
- 插件契约测试：见 §5.3
- 执行引擎集成测试：内置 httptest 起本地服务，端到端运行集合
- CLI 冒烟测试
- 覆盖率门槛：`@apicc/core` ≥ 85%

## 11. 路线图

| 里程碑 | 内容 |
|--------|------|
| M1 本地核心 | 本文档范围 |
| M2 执行引擎与工作流 | Runner 并发调度与采样指标（压测）、DAG 工作流引擎（多入多出、条件流转、草稿→发布→启用生命周期、节点-用例关联影响管理、空过节点置灰）、master/worker 进程模型、CI 触发 |
| M3 在线协作平台 | `StorageAdapter` 在线 DB 实现、Java api-server（认证器抽象、三方认证映射：来源+ID→本地用户 nickname）、项目访问权限与角色、工作区双向迁移（走同一序列化格式）、联机多服务隔离 |
| M4 后台管理 Web | Vue 管理端：用户/项目/权限/执行节点管理 |
| M5 多协议 | gRPC、WebSocket、MQTT、SOAP 作为 `ProtocolClient` 插件 |
| M6 AI 能力 | AI 生成测试用例、agent 导出增强（MCP 工具形态） |
| M7 插件生态 | 插件市场、UI 扩展点、插件开发脚手架 |
