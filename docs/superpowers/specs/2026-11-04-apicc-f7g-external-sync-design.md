# F7g 外部规范同步设计草案 R0

日期：2026-11-04。状态：用户已确认以 R0 为基线，并批准按 [T1–T14 实施计划](../plans/2026-11-04-apicc-f7g-external-sync.md)开工，包含候选分支／PR Windows 打包 CI 调整。Git 集成与每次本地全量仍另行授权。

产品基线 `26063656` 已合并并推送，CI89 五项任务通过；验证约定 `b31b6b1a` 已提交并合并本地 main，尚未推送。本草案基于该本地 main 编写。[复用评估](2026-11-04-apicc-f7g-reuse-assessment.md)记录了已阅读的源码与新增边界。

## 1. 已确认范围与设计目标

用户已确认：

- F7g 包含 URL 和 Git 数据源绑定及手动同步。
- 包含在线项目后台定时检查；检查只生成待确认变更，应用必须由成员明确确认。
- Git HTTPS 和 SSH 均纳入本阶段。
- 日常使用本地定向验证、必要回归与 GitHub CI；任何本地全量及重跑，均须用户明确确认本次范围、原因和预计耗时。

目标：外部规范变化可以持续、安全、可解释地进入 apicc，但 apicc 结构化契约仍是事实来源。检查、预览、应用和回滚分开；本地编辑、用例、工作流、脚本、凭据及既有运行快照不能被静默覆盖。

## 2. 推荐架构与获取位置

采用“来源宿主读取 → 共用 Core 解析与比较 → 固定候选 → 人工决策 → 版本化提交”。

- Core 负责规范归一化、实体匹配、三方比较、决策校验和资产引用检查；不在解析 `$ref` 时自行联网，不执行仓库内容。
- 来源宿主负责网络、Git／SSH 固定操作、凭据、期限、临时文件与取消。桌面和在线私有 Node 服务装配同一套来源宿主与 Core 能力，Java 不复制解析／合并算法。
- Java 负责在线身份、权限、策略、凭据存取、检查领取与持久化事务；在线 Core 操作扩展 F7f 的有限私有 RPC，而不是开放任意命令或任意脚本。
- 本地项目从当前电脑检查，关闭客户端后不承诺继续检查；在线项目建议统一从服务端私有来源宿主检查，后台计划不依赖桌面存活。
- 界面明确显示“检查位置”及可达性。服务端不能访问的来源给出明确诊断，不暗中切换到客户端、不使用成员机器凭据。
- 指定执行代理代抓规范作为后续扩展边界，本草案不把已有测试代理假定为已经具备 Git／SSH 来源任务能力。
- 私有运行服务关闭或版本不兼容时，在线同步检查／比较提前拒绝并说明部署缺项；已有本地功能和无关在线功能保持其既有边界。

## 3. 数据源与只读获取

一个来源绑定一个项目中的明确目标模块与同步范围。多个来源不能默认共同拥有同一个已映射实体；转移来源归属需要显式处理。

| 来源 | 建议配置与固定身份 | 读取边界 |
| --- | --- | --- |
| URL | 地址、认证引用、CA／网络配置；完整内容摘要，辅助记录 ETag／Last-Modified | 有界读取、解析前检查大小和编码；重定向逐跳验证，凭据不跨来源转发；304 不代表当前项目版本下的旧候选仍有效。 |
| Git HTTPS | 仓库、分支／标签、仓库相对入口路径、认证与 CA 引用；最终固定完整 commit 与 blob 摘要 | 仓库只读、按固定提交读取文件；分支或标签之后移动不改变已有候选。 |
| Git SSH | 仓库、用户／主机／端口、引用与相对入口路径、私钥和口令引用、已确认主机密钥材料；固定 commit 与 blob 摘要 | 严格核验主机密钥；未知或变化时停止，不能静默接受或关闭验证。 |

建议首版使用宿主已安装的受支持 Git／OpenSSH，部署镜像显式安装依赖；Windows 客户端提供能力检查和可配置的受信工具路径。缺少工具时只影响对应来源，给出安装／部署诊断；不自动下载安装器，不读取任意仓库指定的可执行程序。

Git 使用隔离的受管理临时对象库和固定操作，不对用户工作仓库执行 pull、reset、checkout 或 push。不读取仓库脚本、Git hooks、外部 diff／过滤器、子模块、LFS 下载器及任意 remote helper；普通 blob 以外的入口、符号链接和越界路径明确拒绝。Git、SSH 参数使用结构化传参和应用控制的配置／凭据桥接，不拼接用户提供的 shell 命令，不继承任意 `ProxyCommand` 或 `GIT_SSH_COMMAND`。

规范版本与保真度沿用已确认的 OpenAPI 导入支持矩阵，逐项报告语义损失；不把“能解析一个 3.x 对象”当作完整支持所有新版本。首版处理单入口文档和内部引用；外部文件／网络引用不能隐式抓取，缺失时说明可用的打包文档处理方式。

## 4. 稳定 ID 与三方比较

比较输入为“上次明确确认的上游基线 B、当前 apicc 项目 L、本次固定上游 R”，不能只比较 L 和 R。

- 为来源、接口、模型、组件、参数、响应及其他可被引用的子实体保留持久映射。ID 属于 apicc，不直接等同于名称、路径或 `operationId`。
- 匹配先使用已确认映射，再结合唯一的外部标识及规范化路由提出建议。重复标识、重命名或歧义要求显式选择，不猜测归并。
- 同一上游重复检查不生成新一套资产 ID、不重复创建接口；接口改名、路由变化不能自动使测试绑定换成其他实体。
- B→R 无变化时保留 L 的本地编辑；仅上游变化生成可采用项；两端同字段不同修改列为冲突；不相交变化仍需进入人工确认的候选。
- 新增／删除、请求与响应、模型、组件、认证声明、示例和元数据分项展示。未被来源拥有的本地用例、脚本、工作流、环境和凭据绑定默认保留。
- 删除或修改可能影响用例、套件、工作流或 Mock 时列出真实引用位置；引用不完整时阻止应用，不靠重建 ID 或删除引用消除错误。

决策建议为“采用来源”“保留当前”或明确建立映射；未解决项不能悄悄跳过后视为已完成。一次确认应覆盖候选中的全部变更决策；用户取消或仅关闭页面不推进比较基线。明确保留当前是对该上游变化的已知本地覆盖，可随本次确认推进上游基线，避免每次检查重复提示同一已解决冲突。

## 5. 固定候选、应用与回滚

候选持久记录来源 ID／修订、获取位置、上游固定版本与完整摘要、映射与基线修订、项目版本、Core 身份、诊断和决策摘要。来源修订、当前资产、映射或权限发生变化时旧候选失效，不能复用旧预览提交。

- 本地复用写入日志与 `expectedRevision`；同步状态、资产变更、映射、基线和历史必须一起提交并能在崩溃后对账。
- 在线在锁外抓取和计算，在短事务内重新检查权限、项目版本、来源代次和候选摘要；资产写入、同步状态、历史、计费与幂等回执原子完成。
- 复用现有资产写入授权与脚本变更分类；同步不能绕过脚本编辑权限、凭据管理权限或成员生命周期。
- 应用与回滚使用稳定操作身份。提交响应丢失后查询回执，不生成新身份重放写入；UI 刷新失败不能让已提交操作再次执行。
- 回滚保留持久的同步前后差异与身份，而非仅存内存 undo token。回滚是一笔新的版本化写入，不把项目版本号倒退。 实施细化：反转该记录的资产变化，保留当前已确认上游基线和映射，视为已知本地覆盖；协调器原子生成新的修订与历史，不把已确认上游认知倒退。
- 首版建议只对目标状态仍匹配该同步提交的记录执行直接回滚；发生后续编辑时拒绝直接恢复并说明冲突，不恢复整份旧工作区覆盖他人修改。
- 已开始的执行使用原固定快照；已发布文档、报告和共享 Mock 副本不随同步自动变化。现有本地 Mock 更新走既有保存与校验流程，不绕开其引用规则。

## 6. 后台检查与权限

后台计划默认关闭，开启后只检查并生成待确认候选，不自动应用、不自动发布、不触发测试或 AI 调用。

- 复用 F7d 的时间规则、时区处理、数据库时间和触发身份约束；同步使用独立有界领取与结果，不伪装为测试 Job，不改变已有测试计划状态机。
- 单来源同时最多一轮有效检查；手动与定时检查共享防重。领取有期限和失效代次，重启后只恢复有资格的检查，不补执行已失效的旧触发。
- 计划暂停、来源变更、成员失权、凭据撤销后，新检查拒绝；在途检查请求取消，迟到结果不得覆盖新来源状态或产生可应用的旧候选。
- 同一上游摘要的重复结果合并记录；新结果不能改变用户正在审阅的固定候选，旧候选明确标为过期／已替代。
- 来源管理、出站检查、应用与回滚接入现有权限解析。项目只读不自动授予使用凭据发起检查的能力；后台检查须有明确授权主体，应用仍检查当前操作者权限。
- Web 管理部署级工具、出站访问策略与工作区额度；客户端项目内配置来源、检查计划、预览和决策。继续保留独立调度驱动扩展边界，暂不实现独立部署调度服务。

建议在现有能力机制中增加下列有限能力，而不是另建一套角色体系；现有 NONE 拒绝、角色下限、显式 deny 优先和成员代次保护继续适用。

| 能力／操作 | 建议内置默认 | 附加约束 |
| --- | --- | --- |
| 读取来源摘要、状态和获授权候选 | 当前项目可读成员 | 不暴露密钥、完整本机路径或超出项目读取权限的原始材料。 |
| `sync.manage`：来源与计划管理 | ADMIN／OWNER 默认允许，EDITOR 默认不授予 | 下限 EDITOR，可由既有能力策略显式委派；不能扩大管理员的出站允许范围。修改凭据值仍另需 `credential.manage`。 |
| `sync.check`：手动或授权后台检查 | EDITOR／ADMIN／OWNER 默认允许 | 下限 EDITOR；后台还需来源管理者明确启用并固定授权主体，不能仅因项目可读就使用项目凭据出站。 |
| `sync.apply`：确认应用与回滚 | EDITOR／ADMIN／OWNER 默认允许 | 下限 EDITOR；每次仍检查项目资产写入资格、来源范围和候选版本，涉及脚本时另查 `script.edit`。 |

后台检查授权失效时记录原因并暂停后续领取，不自动改用另一个管理员身份。定时检查能力与应用能力相互独立，任何后台授权都不包含自动写契约。

## 7. 凭据、网络与资源配置建议

密钥不进入来源 URL、项目定义、普通 RPC 日志、命令行、检查报告或分享副本。同步用途的材料解析单独授权，沿用本机 SecretStore／服务端加密存储；后台检查不能依赖交互口令、本机同名凭据或全局 SSH agent 自动回退。

出站策略按管理员批准的来源／网络范围约束，允许明确配置的内网规范服务，不以统一禁止私有地址取代产品需求。DNS 解析、重定向及最终连接目标均需受控；Git HTTPS 的解析固定与 TLS 校验、SSH 的目标固定与严格主机密钥检查分别验证。HTTP 仅用于策略明确允许的受控场景，认证与 TLS 的必要校验不提供随意关闭入口。

原 R0 数值已随整阶段开工获得用户集中确认；T2 按“有限深度／节点解析预算”和“适合配置的参数应可配置”要求细化了表中规范化深度／节点项。实施计划把配置、单位、合法组合和生效方式落实到真实入口，不把文档或执行裁决冒称产品代码已经实现。

| 配置 | 建议默认 | 建议可配范围／约束 |
| --- | --- | --- |
| 后台计划 | 关闭；启用时预填每小时一次、UTC | 复用六字段 Cron 与时区预览；最小检查间隔 60 秒，受上级频率／容量限制。 |
| 连接超时 | 10 秒 | 1–60 秒，不得大于检查总期限。 |
| URL 检查总期限 | 60 秒 | 5–600 秒，覆盖响应读取与关闭。 |
| Git 检查总期限 | 120 秒 | 10–1800 秒，覆盖获取、对象读取及进程收束。 |
| 只读获取总尝试次数 | 1 次 | 1–3 次，仅对明确的暂态读取失败重试；主机密钥、认证、权限及校验错误不重试。 |
| 规范原文字节预算 | 5 MiB | 64 KiB–16 MiB；解压／解析后同样受归一化和总输入预算约束。 |
| 规范化深度／节点预算（T2 实施细化） | 128 层／100000 个 | 分别为整数 16–256 层、1000–1000000 个；别名按展开后的结构计量，展开前核对并拒绝别名环。独立可配置，不把计数上限冒称操作系统内存硬限制。 |
| 比较总输入／候选输出预算 | 16 MiB／8 MiB | 分别建议 1–64 MiB、256 KiB–32 MiB；实际有效上限还须扣除宿主 RPC 封装并服从其总字节和内存限制，非法组合保存时拒绝。 |
| Git 单次临时材料预算 | 256 MiB | 32 MiB–2 GiB，并预留宿主可用空间；过程监测阈值与部署硬磁盘配额分别显示，不能冒称采样检查是零超量硬保证。 |
| 项目／宿主检查并发 | 1／4 | 项目 1–4、宿主 1–16，受上级额度限制；单来源互斥不能关闭。 |
| 候选有效期 | 24 小时 | 5 分钟–7 天；应用仍重新检查资产与授权版本。 |
| 历史保留 | 30 天、最多 100 条／来源 | 1–365 天、1–1000 条；当前基线、在途操作、仍被引用的回执不可按普通过期记录删除。 |

配置展示默认、已保存、有效值、来源、版本及单位；在途操作固定其开始时配置，调小额度主要作用于新检查。工具路径、网络允许范围和部署硬限制由对应管理员维护；项目成员不能扩大上级范围。

## 8. 页面与验收设计

客户端项目内设置“外部规范同步”入口：来源列表 → 连接／材料诊断 → 检查摘要 → 差异与冲突 → 确认应用 → 历史与回滚。固定搜索与导航、显示来源及检查位置、最近尝试／最近成功时间、短显完整可查的提交指纹和新增／修改／删除／冲突数量。

主视图按业务字段展示来源值、当前值和拟采用值，模型／响应等按层级展开；原始 OpenAPI 或 Schema 可作为专用差异详情。配置、检查状态、轨迹及审计不能以整段 JSON 或含 JSON 的表格单元格代替。中文／English 标签、单位、空态、超额和过期原因必须可读；长内容局部滚动。

必要验收集中覆盖：重复上游稳定 ID、本地独有编辑保留、两端同字段冲突、重命名歧义、依赖删除拒绝、旧候选／旧权限拒绝、应用响应丢失对账、跨重启回滚、后台重启／停用／重复触发，以及 HTTPS CA 与 SSH 主机密钥成功和失败。

验证先运行受影响最小集合和真实边界用例；真实 Git／SSH 使用隔离合成仓库与账号。部署测试使用受信临时 CA／主机密钥，不修改系统全局信任，不以关闭校验换取通过。页面新增内容集中验收，不新增全页面快照或全协议组合矩阵。本地全量是否执行以及每次重跑，均单独向用户说明后确认。

当前基线的 Windows 打包 CI 仅在 main 推送时运行，分支／PR 的绿色结果不等于该项也已通过。用户已在开工确认中批准将打包前移到分支／PR，由 T14 单列实施和验证；这不恢复默认本地全量。

## 9. 范围与下一步

交付顺序为：来源与身份契约 → URL／Git HTTPS／SSH 受控读取与 Core 三方候选 → 本地及在线原子应用／回滚 → 后台检查与权限 → 可读界面、部署与集中验收。[T1–T14 实施计划](../plans/2026-11-04-apicc-f7g-external-sync.md)已列出任务、真实文件、先红用例和检查点；候选与本地存储修订分离、来源读取专用期限、候选分支／PR 打包 CI 安排已随开工获得集中确认。

后续开发沿用 Sol high、独立审核沿用 Sol xhigh；确需临时升级 Sol max 时另向用户申请。常规实现与必要修正按批准的阶段边界连续推进，实质范围变化与新增授权集中说明。

本阶段不加入双向 Git 提交／推送、任意仓库脚本、多文件外部引用自动遍历、自动应用、代理代抓、共享 AI 网关或新脚本沙箱。F7b 三项低优先级遗留仍排在 F7g 后；F7f 两项已知风险仍保持未定因、未修复状态，不因 CI89 通过而关闭。需求池和其他延期项不随 F7g 恢复。

## 10. 已核对的外部接口资料
