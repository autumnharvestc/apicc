# F7f：现有 ACL 复用评估

日期：2026-11-01。基线：`e071f618b95fe874a341a038a5cf12f8303fe3a3`。用户要求在制定 F7f 计划前核实早期 ACL 是否满足当前需求，而非仅因“已有 ACL”就假设可以复用。

结论：**保留账号、成员关系、项目角色覆盖和现有数据主干；不能原样复用整个鉴权链。** F7f 需要统一的项目授权入口、有限业务权限、版本/审计和授权生命周期，并有一处已复现的 OWNER 保护缺口需要前置修正。不是推倒重写，也不是只加几个前端开关。

此文只评估和修订设计。未修改产品/正式测试代码、真实账号、真实数据库或部署；未提交、合并、推送。配套：[F7f 设计 R2](2026-11-01-apicc-f7f-collaboration-design.md)、[整阶段实施计划](../plans/2026-11-01-apicc-f7f-collaboration.md)。用户已明确选择 §7 的 A；下文诊断保留的是修正前的真实旧行为。

## 2. 旧模型的准确语义

| 层次 | 当前行为 | 对 F7f 的意义 |
| --- | --- | --- |
| 平台角色 | `USER/SUPERADMIN`，超管管理账号和部署基础设施；不是自动取得所有工作区业务内容 | 保留；公开分享不转换为平台账号 |
| 工作区角色 | `OWNER/ADMIN/EDITOR/VIEWER`；成员管理、工作区删除/转让等走此层 | 保留主模型，不能拿项目 ADMIN 替代工作区 OWNER |
| 项目 ACL | `NONE/VIEWER/EDITOR/ADMIN`；有覆盖即优先，无覆盖继承工作区角色 | 保留；显式 NONE 与删除覆盖恢复继承不同 |
| 角色覆盖 | 可降级，也可提级，例如工作区 VIEWER 在某项目覆盖为 ADMIN | 保留已存在的明确授予；新业务角色门槛依据有效项目角色，不偷偷改成工作区角色的上限 |
| 成员前置 | 内容、资产和执行入口先要求工作区成员，再算项目角色 | 必须由统一入口保留；单独调用角色计算器不等于通过鉴权 |
| 单点管理 | 工作区 ADMIN/OWNER 可以改项目 ACL；有效项目 ADMIN 可以管理部分项目执行配置 | 保留两个不同管理范围，并明确恢复权限入口 |
| 细粒度能力 | 基本只有 canRead/canWrite/isAdmin/isOwner，执行和凭据写入共用 EDITOR 门槛 | 不足以独立控制脚本编辑、密钥绑定、执行、分享及审计 |

关键源码：[PermissionService](../../../server/src/main/java/com/autumnharvestc/server/core/PermissionService.java)、[WorkspaceGuard](../../../server/src/main/java/com/autumnharvestc/server/workspace/WorkspaceGuard.java)、[ProjectAclService](../../../server/src/main/java/com/autumnharvestc/server/workspace/ProjectAclService.java)、[ContentService](../../../server/src/main/java/com/autumnharvestc/server/content/ContentService.java)、[AgentService](../../../server/src/main/java/com/autumnharvestc/server/execution/agent/AgentService.java)。

## 3. 复用程度：按职责分类，不给虚假的代码百分比

| 部分 | 复用程度 | 必要工作 |
| --- | --- | --- |
| 账号身份、登录 token、停用/撤销基础链 | 高，继续使用 | 后台/分享资格检查也要读当前账号状态；不能只依赖进入 HTTP 时的一次判断 |
| 工作区/项目稳定 ID、角色枚举、ACL 唯一键、内容路径隔离 | 高，保留主干 | 补授权状态/版本等元数据，不把角色枚举无限扩成每种操作一个角色 |
| 角色继承、显式 NONE、删除覆盖恢复继承 | 高，保留语义和现有测试 | 通过统一决策包装使用，分别展示工作区角色、项目覆盖和最终角色 |
| `PermissionService` | 作为底层角色解析器可复用；不能直接当完整安全门 | 外围增加当前账号、成员、对象归属及业务权限统一判断；不让新接口直接调用 effectiveRole 后放行 |
| 成员/ACL 管理 API 与仓储 | 部分复用，需要有界修改 | 增加期望版本、审计与失效联动；明确重新加入语义；覆盖超管备用写入口 |
| 内容/资产/执行/凭据/调度入口 | 复用业务逻辑与已有重检点 | 接入统一授权和对应业务权限；保留调度单独授权与脚本版本批准，不统一成一个“管理员”布尔值 |
| 管理台 ACL 页面及客户端角色展示 | 复用组件、用户搜索和 NONE/继承文案 | 扩展有效来源、权限点、版本冲突、失效状态；管理员项目选择不能只取内容可见树 |
| 分享/Mock 调用授权、发布责任与撤销 | 无可直接复用的等价实现 | 新建与角色 ACL 分离的访问授权、范围、到期、密钥摘要与不可复活失效状态 |
| 可读审计与权限变更历史 | 现有 execution 事件可部分复用 | 成员/ACL/凭据/新授权补真实事件，必要变更与审计同事务，不补造旧历史 |

建议是“保留模型与数据、收拢判断、扩展能力和治理”，而非另装整套通用权限框架或重写所有服务。

## 4. 已确认的语义差异和缺口

### ACL-E01：非成员预设 ACL，不等于非成员实际获准访问

现有 `ProjectAclService.put` 只要求目标账号存在，不要求是成员；`PermissionService.effectiveRole` 对这种记录可以返回 ADMIN。其单测 `aclRowGrantsNonMember` 也明确覆盖这一点。

真实 HTTP 诊断结果：先为非成员设置项目 ADMIN 成功，但该账号读取 `tree` 和项目 `assets` 均为 **403**。原因是这些入口还会执行工作区成员守卫。

这是“角色解析”与“实际准入”两层语义，不是已发现非成员越权。F7f 不能把角色解析器直接复用于分享资格、后台责任人或能力列表；也不能把预设 ACL 显示成“此人已经可以访问”。新增业务授权只向当前有效成员授予；旧预设记录应明确显示尚未生效及其处理口径。

### ACL-E02：移除后保留 ACL，重新加入会自动恢复

[MemberService.delete](../../../server/src/main/java/com/autumnharvestc/server/workspace/MemberService.java) 只删成员行；`ContentService` 的旧注释明确约定重新加入恢复 ACL。这不是本次新回归，也不能仅因测试通过就认为符合 F7f。

真实 HTTP 序列：工作区 VIEWER＋项目 ADMIN → 移除成员 → 内容树 403 → 再以 VIEWER 加入 → 项目角色重新变为 **ADMIN**。

影响：新增分享的责任人若只检查“当前是否又有权限”，其离开/重新加入可能使旧外链恢复；新业务权限若仿照保留 allow 记录，也可能复活。F7f 分享/调用秘密必须有独立、不可被重新加入自动复活的撤销代次或终态；仅查询当前角色不够。

旧 ACL 的重新加入行为属于需要用户明确选择的产品口径，见 §7；本轮不擅自清理已有 ACL。

### ACL-E03：组织目录、内容树与管理权限不是同一集合

[ProjectService.list](../../../server/src/main/java/com/autumnharvestc/server/workspace/ProjectService.java) 向成员列出组织项目元数据；`ContentService.tree` 则按项目 ACL 过滤内容可见项。工作区管理员改 ACL 的权限按工作区角色判断，不要求其当前能读目标项目内容。

真实 HTTP 诊断：工作区 OWNER 给自己设置项目 NONE 后，内容树不含该项目，但组织目录仍含项目，ACL 管理读取仍为 **200**。这符合当前两个不同入口的实现，并不能用“有元数据”推断“可以读内容”。

管理台 `ProjectAclView.vue` 的项目下拉来自内容树，故源码显示有一处恢复入口适配缺口：管理员被某项目 NONE 限制后，API 尚能修改 ACL，但该下拉可能没有该项目。本轮证实了服务端数据差异，未冒称做过该情形的真实浏览器交互。

F7f 应提供管理目录与内容目录分离的投影：内容、报告、分享来源只取有权集合；工作区 ACL 恢复页取有管理权的目录。页面分别显示“可管理权限/不可读内容”，不能为了让下拉可选而授予内容读取。

### ACL-E04：OWNER 保护存在已复现的备用入口缺口

普通成员 API 会拒绝变更当前 OWNER；但[AdminService.setWorkspaceRole](../../../server/src/main/java/com/autumnharvestc/server/admin/AdminService.java) 只限制新角色载荷，不检查目标当前是否 OWNER，最终直接 `memberships.upsert`。

真实回环 HTTP 诊断结果：

| 操作 | 返回 | 实际数据 |
| --- | --- | --- |
| 普通成员 API：OWNER 改为 VIEWER | 403 | OWNER 仍在 |
| 平台超管入区定角色 API：同一 OWNER 改为 VIEWER | 204 | 当前成员角色为 VIEWER，工作区 OWNER 数从 1 变为 0 |

一次性诊断对此 OWNER 不变量断言失败，实际 **exit 1**；没有修复，也没有撤销断言换取通过。它要求有效 SUPERADMIN，并非匿名权限绕过；缺陷是绕过现有 OWNER 不可变/转让路径，使工作区失去所有者。

现有 `AdminUsersApiTest` 检查的是“传入 role=OWNER 被拒绝”，没有覆盖“目标原本是 OWNER、传入 VIEWER”；这解释了原有相关回归仍能通过。

建议列为 F7f 权限基础的前置有界修正：先在真实管理员 API 测试中保留该失败，再统一各成员写入口的 OWNER 保护和转让约束。未因此授权直接修改产品。

### ACL-E05：旧 ACL 缺少版本与必要事务审计

旧请求为 `userId+role`，响应为 `userId+role`，没有 `expectedVersion`、变更人或权限来源；写覆盖基本按最后写入生效。成员转让是先升后降两次写，旧实现有意未使用事务。不能在增加审计时直接加一个注解就假定治理完善。

[AclRepo.upsert](../../../server/src/main/java/com/autumnharvestc/server/store/AclRepo.java) 还记录了“捕获重复插入再 UPDATE”与未来 PostgreSQL 显式事务的限制。本期实际仍是 H2，不据此声称已兼容 PostgreSQL，也不擅自新增数据库迁移专项。

F7f 必须在同一授权变更权威里校验版本、写角色/能力、记录审计及失效依赖。仓储实现需适配所选事务方式；旧 PUT/batch、超管入区、成员转让/移除等不能成为绕过路径。旧 batch 部分成功语义保持，按每个实际条目完成授权/提交，不静默改为整批事务。

### ACL-E06：粗角色无法表达新业务权限，已有独立授权也不能抹掉

现在 `EDITOR` 同时意味着多数内容写、任务执行和项目凭据绑定写；脚本字段还可能通过旧文件接口修改。这不能表达“可以维护契约，但不能改脚本/凭据”或“可读报告，但不能对外分享”。

F7d 已有独立调度管理授权和执行主体校验；F7b 已有节点策略＋脚本版本批准。这些应复用，并与新增权限取交集，不能因引入一个 `task.execute` 就删除原有批准链。

## 5. 推荐复用架构

在 Java 内增加统一 `ProjectAccessService`（名称为设计建议），组合已有 Role/ACL 解析和新的业务权限。旧 `PermissionService` 保留为角色解析；Node 只做声明式内容判断/投影，不成为第二套角色权威。

对业务入口返回内部决策：账号可用性、成员资格、工作区角色、项目覆盖与来源、有效项目角色、能力/限制、授权修订及稳定拒绝原因。对前端只输出该用户获准查看的可读能力与来源，不暴露他人权限或私有策略材料。

最低接线清单：

1. 成员/项目 ACL、超管停用/入区/改角色：所有真实变更进入一致的版本、审计、失效处理；OWNER 边界不只在一个控制器检查。
2. 内容同步及原子项目 delta：覆盖真实脚本字段变化、删除与旧 JS 条件；未知布局缺权限先拒绝，不能靠文件名猜。
3. 本机/代理的准备、提交、启动、材料领取与取消：复用原有固定任务、脚本批准和最新资格重检点，不重写任务状态机或去重账本。
4. 任务历史、归档报告、调度历史/通知及 CLI/MCP 上游：按对象检查对应历史权限；有权执行者仍可观察自己的最小在途状态，不能变成盲执行。
5. 凭据管理：独立写/删权限；角色和分享权限不产生原文读取能力。
6. 公开分享/Mock：独立授权对象、专用秘密与责任人资格，无成员身份转换；撤销与资格失效不能由旧 allow 记录复活。
7. 管理台/客户端：以服务端能力与来源驱动，角色 UI 只是提示，不能作为权威；管理目录和内容目录分离。

对并发的承诺要可验：等待项目锁或异步 Node 检查后，提交前重新核对修订和当前资格。已经通过准入的响应/在途业务不声称可被角色变更远程收回；新的准入不能沿用旧允许缓存。

## 6. 新增到实施计划的前置准入

建议把“权限基础适配”放在发布/外链/Mock 之前，不等最后联验才处理：

- 有效失败测试先覆盖 OWNER 备用入口缺口；原有角色解析、NONE/继承与基础隔离保持回归。
- 明确成员生命周期选择后，复现“移除—重新加入—旧角色/新权限/外链”并检查是否符合该选择；不是仅断言 GET 返回一个字段。
- 三种管理视角各一个必要案例：工作区管理员可修 ACL 但无内容权、项目管理员不能改工作区成员、EDITOR 被单独撤销脚本/凭据/执行某一权限仍能做剩余动作。
- 权限变更冲突、审计失败回滚及一次受控权限变更/提交交错；不扩成全角色×所有端点组合矩阵。
- 外链撤销/失权不可复活与公开 DTO 边界仍按 F7f AC；F7b 三项延期及其他专项不因此恢复。

本次原有定向回归只说明旧行为基线稳定。新的保护和新角色/能力组合仍须在正式实施时先复现、实现、定向审核；不能把本次诊断或补测笼统宣称为整个 F7f 已完成 TDD。

## 7. 已确认的产品口径：移除后的旧 ACL

用户选择 **A：旧显式授权失效，重新加入后由管理员重新确认**：移除立即使旧 allow/角色覆盖和新增业务授权失效；已有 NONE 拒绝保持明确，不能因删除记录意外回退为更宽的工作区继承。重新加入时有旧显式覆盖的项目显示“待重新确认”，不会自动恢复原 ADMIN/EDITOR；无旧覆盖的项目按新工作区角色和当前策略计算。管理员可明确恢复某项覆盖，或确认恢复继承。此方案需要状态/代次及 UI 说明，而非简单删除所有 ACL 行。

历史备选 **B：保留旧 ACL 自动恢复，但新增业务授权和外链单独失效**，本阶段不采用：改动较少，但以 VIEWER 重新加入仍可能因旧 ACL 变为某项目 ADMIN。已撤销外链/Mock 秘密均不可自动恢复。

这项是用户明确批准的旧行为变更，不是已经实现的修复。其他结论支持“模型高复用、鉴权入口有界整合、治理与分享授权新增”，不需要因此重做账号/存储/执行内核。产品开发仍等待整阶段计划集中确认。
