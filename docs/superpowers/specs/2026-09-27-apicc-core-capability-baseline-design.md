# apicc 核心能力基线设计规格

> 状态：已批准进入规划
>
> 日期：2026-09-27
>
> 目标：把 apicc 从“功能闭环原型”推进为结果可信、编排可靠、压测可用于工程决策的 API 测试开发平台。

## 1. 背景与问题

apicc 已建立本地优先、文本资产、Git 友好、core/CLI/desktop 分层的基础，并具备接口调试、自动化测试、工作流、基础压测、协作服务端和管理后台。现阶段的主要矛盾已经不是“有没有入口”，而是核心执行结果是否真实、不同入口语义是否一致，以及需求是否足以支撑生产使用。

本规格将产品目标重新收敛为三个核心价值：

1. **测试可信**：同一个用例在单次运行、集合运行、工作流和压测中具有明确且一致的语义，失败后能够诊断；
2. **编排可靠**：场景不仅能画 DAG，还能表达并行、汇聚、循环、重试、超时和错误处理；
3. **压测可决策**：负载模型、连接模型、成功判定、阈值和报告足以支撑容量与回归判断。

协作、权限、管理后台继续作为平台能力保留，但在核心执行能力达到本规格的正式版门槛前，不作为主要研发投入方向。

## 2. 产品定位与用户

### 2.1 产品定位

apicc 是本地优先、可进入 Git 和 CI 的 API 测试开发平台。它帮助团队把接口定义、功能用例、端到端场景和性能场景作为同一套可审查资产管理，并在桌面端与命令行中得到一致结果。

### 2.2 优先用户

| 优先级 | 用户 | 核心任务 |
|---|---|---|
| P0 | API 开发工程师 | 调试接口、保存示例、编写断言、定位失败、在提交前运行回归 |
| P0 | 测试工程师 | 参数化用例、组织测试套件、编排业务场景、输出 CI 报告 |
| P0 | 性能工程师 | 定义负载、维护虚拟用户会话、设置 SLA、比较性能基线 |
| P1 | 团队管理员 | 管理账号、工作区、权限、项目同步和运行资产 |
| P2 | 插件开发者 | 扩展协议、认证、断言、报告和存储能力 |

## 3. 设计原则

1. **可信优先于功能数量**：显示出来的用例、成功率、分位数和退出码必须与真实执行一致。
2. **同一语义内核**：功能测试、工作流与压测共享请求构建、脚本、断言和变量规则，差异通过明确配置表达。
3. **运行状态隔离**：变量、cookie、连接、数据行游标和操作生命周期属于单次运行或单个虚拟用户，不存入可复用 runner 实例。
4. **报告可解释**：任何失败都能追溯到请求、响应、脚本、断言、节点或负载阶段；敏感信息必须脱敏。
5. **开放模型与持久化一致**：插件可注册的类型必须能被工作区 schema、桌面端和 CLI 表达、保存并执行。
6. **渐进兼容**：现有工作区和旧报告继续可读取；格式升级必须有显式版本与迁移规则。
7. **安全发压**：压测默认保护非本地目标和生产标记环境，避免误发流量。

## 4. 统一执行语义

### 4.1 用例执行模型

每个用例执行必须经过同一条语义链：

1. 创建运行上下文；
2. 注入环境、模块、项目、用例参数和数据行；
3. 执行容器级与用例级前置操作；
4. 构建并发送请求；
5. 保存响应；
6. 执行后置操作和声明式提取；
7. 执行声明式断言和脚本断言；
8. 产出包含诊断证据的结果；
9. 执行结束/清理操作。

单次调试可以选择只发送请求；一旦入口命名为“运行用例”或“压测用例”，必须执行上述用例语义，不能只校验用例 ID 是否存在。

### 4.2 生命周期

- 单次用例运行：一个运行上下文；
- 集合运行：一个集合上下文，每个用例/数据行创建子上下文；
- 工作流运行：一个工作流上下文，每个节点创建子上下文；
- 压测运行：每个虚拟用户创建独立上下文，连接、cookie、持久变量和数据游标不得跨虚拟用户共享；
- 容器前置/后置操作在功能测试中按容器生命周期执行，在压测中按虚拟用户生命周期执行；
- 用例前置/后置操作在每次迭代执行。

### 4.3 时间指标

压测必须区分：

- `requestTimeMs`：请求发送到响应体按策略读取完成的网络时间；
- `iterationTimeMs`：前置操作、请求、后置操作和断言的完整迭代时间；
- 报告的 HTTP 延迟分位数默认使用 `requestTimeMs`；
- 生成器开销使用两者差值和进程资源指标辅助诊断。

## 5. 功能需求

### 5.1 执行可信度（EXEC）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| EXEC-001 | P0 | 压测必须执行所选用例的参数、前后置操作、数据行和断言 | 同一夹具经功能运行与单并发单迭代压测得到相同请求和断言结论 |
| EXEC-002 | P0 | 运行上下文必须按 run/节点/虚拟用户隔离 | 并行运行两个不同 globals 的集合无串扰；两个虚拟用户的 cookie/变量互不可见 |
| EXEC-003 | P0 | 运行结果必须区分网络、HTTP、脚本、断言、配置和中止错误 | 报告及 CLI 摘要分别统计各类失败 |
| EXEC-004 | P0 | 功能、工作流、压测入口的退出语义必须可预测 | 未满足强制断言/阈值/引用完整性时返回非零；预期条件剪枝不误判 |

### 5.2 HTTP 与会话（HTTP）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| HTTP-001 | P0 | HTTP 客户端默认复用连接池，按运行生命周期关闭 | 本地服务器记录固定并发多次请求复用连接；停止运行后连接可释放 |
| HTTP-002 | P0 | 连接复用模式与强制新连接模式可配置 | 两种模式分别有连接计数测试，报告记录模式 |
| HTTP-003 | P1 | 支持 cookie jar 和每虚拟用户会话 | 登录后续请求自动带 cookie，不同虚拟用户隔离 |
| HTTP-004 | P1 | 支持 multipart/form-data 和文件上传 | 文本字段与文件字段能被标准测试服务正确接收 |
| HTTP-005 | P1 | 支持 OAuth 2.0、代理、重定向、自定义 CA 和 mTLS | 每种能力至少有契约测试和错误诊断 |
| HTTP-006 | P1 | 请求级连接、响应头、响应体和总超时可配置 | 四类超时能被区分并报告 |

### 5.3 功能测试（TEST）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| TEST-001 | P0 | 失败结果保存脱敏后的请求、响应、断言、脚本日志和提取值 | CI 报告无需本机复现即可看见失败证据，secret 不出现 |
| TEST-002 | P1 | 支持 exists、not-exists、regex、长度、集合、深比较、cookie、XPath | 每种断言可在 schema、CLI、桌面端创建和执行 |
| TEST-003 | P1 | 支持声明式 JSONPath/XPath/正则变量提取 | 无需脚本即可把响应值传给后续用例/节点 |
| TEST-004 | P1 | 支持 JSON Schema/OpenAPI 响应验证 | schema 不匹配可定位到字段路径 |
| TEST-005 | P1 | 支持标签、筛选、测试套件和测试计划 | CLI 与桌面端对同一选择集执行一致 |
| TEST-006 | P1 | 支持历史趋势、基线对比和失败聚类 | 可比较两个运行的通过率和耗时变化 |

### 5.4 工作流编排（WF）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| WF-001 | P0 | 数据驱动节点按全部数据行聚合结果 | 任一行失败则节点失败，逐行结果完整保留 |
| WF-002 | P0 | 区分预期条件剪枝、引用缺失和异常跳过 | strict 模式下引用缺失非零退出，条件剪枝保持 skipped |
| WF-003 | P1 | 支持真实并行分支及 AND/OR 汇聚 | 两个延时分支墙钟时间证明并行；汇聚组合测试通过 |
| WF-004 | P1 | 支持 script、set-variable、delay、assert、foreach、sub-workflow 节点 | 每类节点可保存、校验、运行和显示结果 |
| WF-005 | P1 | 节点支持超时、重试、退避、错误路由和 finally | 重试次数、等待时间和最终状态可追踪 |
| WF-006 | P1 | 工作流支持输入、局部变量、输出和初始化/结束操作 | 子工作流参数边界明确，无隐式全局串扰 |
| WF-007 | P1 | 支持运行轨迹、节点重跑和断点调试 | 用户能从失败节点继续且看到使用的上下文快照 |
| WF-008 | P1 | 工作流可作为压测场景 | 每虚拟用户独立执行完整场景并输出步骤级指标 |

### 5.5 压测（STRESS）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| STRESS-001 | P0 | 成功判定同时考虑传输、HTTP、脚本和断言 | HTTP 200 但断言失败进入 assertionFailed，不计业务成功 |
| STRESS-002 | P0 | 支持 p95、错误率、断言失败率、最低 RPS 阈值 | 任一必选阈值失败，报告 verdict 失败且 CLI 非零退出 |
| STRESS-003 | P1 | 支持固定并发、恒定到达率和多阶段负载 | 实际到达率在生成器未饱和时与目标误差不超过 5% |
| STRESS-004 | P1 | 支持 warm-up、think time、pacing、最大虚拟用户和优雅停止 | 各参数在报告中留存，停止不再发新请求并可中止在途请求 |
| STRESS-005 | P1 | 采用有界内存的流式指标与可合并直方图 | 一百万样本运行时内存不随原始样本线性增长 |
| STRESS-006 | P1 | 报告包含吞吐、延迟、错误的时间序列和阶段对比 | 桌面端能显示趋势图、阈值和失败阶段 |
| STRESS-007 | P1 | 远程 agent 支持注册、心跳、容量、同步起跑和完整性标记 | agent 丢失时报告标记不完整并非零退出 |
| STRESS-008 | P1 | 支持报告基线比较 | 可按环境与场景比较 RPS、p95 和错误率变化 |
| STRESS-009 | P0 | 对生产标记或非本地目标启用发压保护 | 未明确确认时拒绝运行；CLI 支持显式受审计覆盖参数 |

### 5.6 插件与模型（EXT）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| EXT-001 | P0 | 注册的新断言操作符可被 schema 保存和加载 | 内置 xpath 与示例 hasField 均可通过工作区 schema 往返 |
| EXT-002 | P1 | 协议和认证扩展可携带插件配置 schema | 插件类型能在 CLI 与桌面端编辑，非法配置在执行前报错 |
| EXT-003 | P1 | 工作区记录所需插件及版本范围 | 缺插件时给出可诊断问题，不静默丢字段 |

### 5.7 安全与工程（SEC/ENG）

| ID | 优先级 | 需求 | 验收 |
|---|---|---|---|
| SEC-001 | P0 | secret 不以明文进入工作区、日志、报告和导出 | 自动化扫描夹具 token，所有产物只出现掩码 |
| SEC-002 | P1 | 插件信任边界和权限可见 | 启用插件前展示能力，禁用后不再加载 |
| ENG-001 | P0 | Windows 本地总测试命令稳定 | 连续三次执行根级测试均无共享 JAR 竞争 |
| ENG-002 | P0 | JDK 21 是服务端唯一支持构建基线 | CI 与本地文档均使用 `JAVA_HOME` 根目录，版本检查 fail-fast |
| ENG-003 | P1 | 工作区和报告格式显式版本化 | 旧格式有迁移测试，新版本不可被旧代码静默破坏 |

## 6. 非功能性要求

### 6.1 平台与兼容

- Node.js 最低版本保持 `22.19.0`；
- 服务端构建与运行基线为 JDK 21；
- 正式支持 Windows；macOS/Linux 在发布前通过构建与核心无界面测试；
- 现有无版本工作区在引入格式版本时自动识别为 v1，并经显式迁移保存为新版本。

### 6.2 规模基线

- 单机压测至少支持 1,000 并发连接的配置表达；实际能力由生成器资源报告说明，不承诺每台机器均达到同一 RPS；
- 单次压测至少支持 24 小时持续运行，聚合内存保持有界；
- 工作流至少支持 500 个节点的加载与校验，执行并行度可配置；
- 单个功能测试响应快照默认上限 1 MiB，超出部分截断并记录原始长度；
- secret 脱敏在写日志、写报告、事件广播之前完成。

### 6.3 可观测性

- 每次 run 有稳定 `runId`；工作流节点、虚拟用户、迭代和请求可关联；
- 错误分类使用稳定机器码与中文说明；
- 报告包含执行配置、软件版本、开始/结束时间和数据完整性状态；
- 压测报告包含生成器 CPU、内存、事件循环延迟和网络错误摘要。

## 7. 版本与兼容策略

1. 新增字段优先以 optional 方式读取旧产物，新写产物携带明确版本；
2. 分布式 worker 协议从 v1 升级时，协调器必须拒绝不兼容版本，而不是猜测字段；
3. 断言 `op` 从固定枚举迁移为受注册表验证的字符串；核心断言仍保留内置清单；
4. 旧压测报告缺少 verdict 时显示“未评估”，不得自动判为通过；
5. README 对实验性能力使用“基础”“本地分片”等准确词语，达到验收后再升级表述。

## 8. 交付阶段与依赖

| 阶段 | 名称 | 必须完成的需求 | 依赖 |
|---|---|---|---|
| A | 压测执行可信度 | EXEC-001/002/003/004、HTTP-001/002、STRESS-001/002、STRESS-009 | 无，第一实施计划覆盖 |
| B | 工作流正确性 | EXEC-002/004、WF-001/002、ENG-001 | A 的运行上下文边界 |
| C | 测试诊断与扩展一致性 | TEST-001/002/003、EXT-001、SEC-001 | A 的统一结果类型 |

| E | 强编排 | WF-003 至 WF-007 | B 的状态语义与 run context |
| F | 专业压测 | STRESS-003 至 STRESS-008、WF-008 | A、D、E |

每个阶段使用独立实现计划和审查检查点。阶段 A 是当前唯一进入详细实现计划的范围，避免同时改动压测、工作流、报告和协作四个子系统。

## 9. 阶段 A 的设计裁定

### 9.1 HTTP 客户端

- 新增可实例化的 `createHttpClient()`；客户端拥有 Agent 生命周期；
- 默认模式按 timeout profile 复用 Agent，Undici Agent 自行按 origin 建池；
- `connectionMode: "pooled" | "fresh"` 明确控制复用；
- 现有 `httpClient` 保留为默认共享实例，保证调用方兼容；
- 压测使用 run-scoped HTTP client，并在运行结束后关闭；
- 每请求不再创建并立即关闭 Agent。

### 9.2 用例执行内核

- 从 `CollectionRunner` 提取无跨 run 实例状态的 case executor；
- executor 输入包含 API、用例、数据行、变量解析器、globals、持久变量和依赖；
- executor 输出包含 `CaseOutcome`、响应元数据、`requestTimeMs` 和错误分类；
- 集合运行和压测均调用该 executor，防止两套脚本/断言语义继续漂移；
- 压测每个 worker 创建自己的虚拟用户 session，session 持有独立变量和数据游标。

### 9.3 压测结果与阈值

- `StressSample` 增加 `requestTimeMs`、`iterationTimeMs` 和结果分类；
- `ok` 表示传输、HTTP、脚本和断言全部成功；
- 报告分列 `transportFailed`、`httpFailed`、`scriptFailed`、`assertionFailed`；
- 阈值在聚合结束后评估，得到 `verdict: { passed, violations }`；
- CLI 未提供阈值时仍按“存在业务失败即非零”处理，不再只有全部失败才返回非零；
- 桌面端显示 verdict 和失败分类。

### 9.4 安全发压

- 环境增加可选 `production: boolean`，默认 false；
- 目标 host 非 loopback，或环境标记 production 时，桌面端要求二次确认；
- CLI 要求显式 `--allow-production`；
- 是否覆盖保护写入报告配置。

## 10. 非目标

阶段 A 不实现以下能力，但本规格已固定其后续位置：

- 恒定到达率、多阶段曲线和时间序列；
- 远程分布式 agent；
- 工作流并行网关和工作流级压测；
- multipart、OAuth2、cookie jar、mTLS；
- 完整 secret vault；
- 报告历史基线比较。

阶段 A 不新增协作服务端接口，不改变账号、RBAC、在线工作区和管理后台。

## 11. 发布门槛

阶段 A 只有同时满足以下条件才可宣称完成：

1. HTTP 连接复用测试证明 pooled 模式复用连接，fresh 模式不复用；
2. 同一用例经集合运行和单并发单迭代压测，实际请求、脚本副作用和断言结论一致；
3. HTTP 200 + 断言失败时压测报告失败且 CLI 非零；
4. 阈值失败时 CLI 非零，桌面端显示具体 violation；
5. 两个并发虚拟用户的变量、cookie 占位状态和数据游标隔离；
6. 停止或完成后 run-scoped HTTP client 被关闭；
7. 单 shard 与本地多 shard 的统计和退出语义一致；
8. core、CLI、desktop 相关测试与构建通过；
9. README 将未完成的远程分布式能力准确标为本地多进程分片。
