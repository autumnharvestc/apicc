## 1. 已确认方向

- 独立部署执行代理（Runner Agent），复用现有 TypeScript Core；Java 后端承担控制服务，不另外实现请求、断言、测试计划或编排算法。
- 一个项目可配置多个代理，用户可以选择由哪个代理执行，面向不同测试网络的可达性及网络时延问题。
- 代理主动连接自托管 apicc 后端，首版采用 HTTPS 长轮询领取任务，而非固定间隔查询。
- 保留以后切换到长连接的平滑演进空间；当前不实现长连接，不提供尚不可用的传输选项。
- 代理配置管理和项目关联统一在 Web 管理页面操作，由对应级别的管理员负责；桌面端不重复建设代理管理面。
- 管理入口的上述约定只针对代理基础设施，不把接口认证、环境变量和测试参数迁往 Web 管理后台；这些日常测试配置仍在客户端对应项目中操作。

## 2. 避免未来大改的设计边界

| 层次 | 职责 | 切换长连接时 |
| --- | --- | --- |
| Core 执行内核 | 请求、断言、提取、测试计划、工作流及已有报告语义 | 不因通信方式变化而修改或复制 |
| 任务协议与执行宿主 | 任务身份、快照、领取与确认、生命周期、取消、进度、结果及恢复对账 | 保持同一业务语义，不以 HTTP 连接状态代替任务状态 |
| 传输适配 | 首版长轮询的等待、超时、发送、接收及重连 | 后续新增长连接适配，复用上述协议与宿主 |

以下是据已确认方向形成的设计约束，供后续完整规格落实，不是本轮代码或已验证能力：

1. **业务消息不绑定 HTTP。** 任务、执行批次、消息身份、确认与顺序属于版本化任务协议；具体字段与 Schema 在整阶段设计中冻结。长轮询返回体与未来长连接消息使用同一业务定义，不分别发展两套任务模型。
2. **连接不等于执行所有权。** 领取、开始、取消及完成均有明确的业务确认与持久状态；请求返回或连接关闭本身不表示任务已经执行、取消或结束。
3. **断线重连与消息重发不重新运行任务。** 用稳定任务/执行批次/消息身份做对账与去重；不能把相同参数的两个合法新任务误判为同一任务，也不承诺目标业务请求恰好执行一次。
4. **控制与大文件传输解耦。** 快照、附件和报告通过独立 HTTPS 传输接口获取或上传，控制消息携带引用、版本及完整性信息；以后改用长连接，不要求把大文件塞进长连接消息或改变 Core 输入。
5. **传输选择集中装配。** 执行器与调度逻辑依赖任务通信边界，不遍布 long-poll / WebSocket 判断。只提取当前确有必要的接缝，不实现未来适配器、空壳功能或通用传输框架。
6. **未来按代理会话协商迁移。** 长连接仍由代理主动建立。后端可在迁移期兼容不同代理的传输方式；单个代理不能因双通道同时领任务而重复执行。在途任务不因切换被重新创建，具体交接规则随长连接需求另行设计。
7. **长轮询只是等待新工作。** 有任务则尽快返回，无任务才等待至超时；等待使用异步机制。网关超时、退避重连、心跳、消息确认及结果上传各自定义，不依靠一个永不掉线的连接提供可靠性。

## 3. 与断线策略、既有代码的关系

- 前面讨论的建议仍是完整设计输入：完整接单后可在控制链路断开时继续本地执行，结果有界持久缓存并补传；后端显示状态待确认，不因失联自动换代理重跑。取消不能在断网时承诺立即生效，任务必须有代理可独立执行的本地超时。完整状态转换和容量策略仍需随整阶段规格统一审查。
- 代理到目标接口的网络失败与代理到后端的控制链路失败分别处理；后者的通信重试不能偷偷重试目标业务请求。
- 整份执行计划由选定代理调用 Core 本地运行，不将后端逐条指挥请求的网络延迟引入接口计时和压测调度。
- 现有 Core 本机压测 worker IPC 保持内部职责，不直接扩展为远程代理协议；本机共享时钟能力不能用于不同机器。
- 首版多代理选择不等于跨代理分布式压测。DEF-001 受限脚本/WASM 专项继续无限期延期，不以服务端代理建设为由恢复。

## 4. 管理入口与管理员分工

### 用户已确认

- Web 管理端负责代理配置管理与项目关联，不在桌面端另做一套管理流程。
- 相关管理操作受管理员级别及其管理范围约束；不能因为登录了管理页面就获得全部代理或项目的管理权。
- 桌面端保留已授权代理的选择、任务提交和结果查看；这不授予代理配置或项目关联的修改权限。

### 已确认的管理员分层

现有角色依据：平台 `USER / SUPERADMIN`，工作区 `OWNER / ADMIN / EDITOR / VIEWER`，项目 ACL `NONE / VIEWER / EDITOR / ADMIN`。现有项目 ACL 的 ADMIN 主要影响内容权限，不等于已经实现下述代理管理权限；新增操作必须明确授权规则。

| 管理范围 | 角色 | 操作边界 |
| --- | --- | --- |
| 平台级 | SUPERADMIN | 登记代理、节点级配置、启停接单、撤销代理身份、授予工作区使用范围 |
| 工作区级 | 工作区 OWNER / ADMIN | 管理已授予本工作区的代理使用范围及区内项目分配；不跨区授权或修改其他区共用代理的全局配置 |
| 项目级 | 该项目有效 OWNER / ADMIN | 仅从工作区已授权代理中维护本项目关联和默认选择；不能扩大代理授权范围 |
| 任务使用（具体授权待完整规格定义） | 具备任务执行权限的项目成员 | 选择本项目已授权且适用的代理提交任务、查看有权读取的结果；不能管理代理或项目关联 |

- 平台代理管理权限不自动授予项目资产读取、凭据查看或任务执行权限；具体任务权限在整阶段规格中另行定义。
- Web 隐藏按钮不是权限边界；后端管理 API、任务准入及代理领取任务均核对作用域，不能只依靠客户端提交的代理 ID。
- 建议代理本机只保留连接后端所需的最小部署引导配置；已连接代理的可管理运行参数在 Web 维护。部署引导配置、可管理字段及共享代理/项目级参数的覆盖关系在完整规格中明确，不承诺 Web 能管理尚未建立连接的代理。
- 配置变更、项目关联和默认代理变更须可审计。记录接单时配置身份，启动前核对最新授权与额度，已开始任务固定实际执行参数；不能由后续 Web 配置修改静默改变在途执行。

### 配置入口、执行位置与凭据保存分别设计

前一轮“Web 统一维护被测接口 token/密码，再在后端托管与代理托管之间二选一”的建议未获批准；用户指出混淆了代理管理与项目认证配置。该建议撤回，由下述分层设计替代，不能在后续规格中将其当作已确认决策。

#### 本轮澄清的产品边界

- Web 管理后台：代理登记、节点级配置、工作区授权及项目关联，由对应级别管理员操作。
- 客户端项目工作区：接口认证、环境变量、测试参数及数据配置，按项目权限操作；不要求日常测试人员切换到管理后台填写 token/密码。
- 客户端运行入口：环境和执行位置分别选择。本机执行时由当前电脑调用 Core 发往目标接口；代理执行时由选中代理调用同一 Core 发往目标接口。后端是资产与控制服务，不是目标接口请求的必经转发站。
- 切换执行位置不能静默切换环境、替换凭据或在代理不可用时自动改为本机执行。

#### 已确认的保存策略（尚未实现）

| 凭据使用范围 | 配置入口与保存位置 | 执行适用范围 |
| --- | --- | --- |
| 在线项目凭据 | 在客户端该在线项目内配置；后端加密保存值，项目资产保存引用；受项目及任务授权控制 | 在线项目的本机执行和授权代理执行可按需装配 |
| 仅本机凭据 | 同一客户端项目配置入口中显式选择仅本机；由当前电脑加密保存 | 仅本机执行，不自动上传或转交代理 |

- 用户确认这套分层：在线项目的常用团队测试凭据默认采用项目范围，并明确显示保存范围；个人临时凭据可选仅本机。两者均从客户端对应项目配置，不迁移到 Web 管理后台填写。
- 普通本地项目继续沿用现有本机存取策略，打开在线项目不会自动迁移既有桌面凭据。
- 本机执行并不要求所有配置都仅存于本机：它可在准入时取得已授权的在线项目快照及项目凭据，而目标请求仍由本机直接发送。
- 若选中代理但任务引用了仅本机凭据，应在执行前明确提示并要求用户改用项目凭据或本机执行，不静默上传、不移除认证继续请求，也不换用同名凭据。
- 两条执行路径均由宿主装配 Core 的 credentialBindings，存取策略与 Core 语义分离；沿用加密保存、无需主动解锁的体验。后端是能接触其托管凭据的受信组件，不宣称无法解密。
- 凭据原值不混入普通项目文件、通用任务快照或报告；具体值的授权交付、缓存和清理在完整规格中明确。此处讨论非脚本请求认证，不恢复延期的脚本密钥专项。

## 6. 运行参数可配置要求

用户补充确认：适合做成配置项的参数必须可配置，方便按需要调整，不能将建议默认值写死。

- 包含代理同时执行任务数、长轮询/心跳/失联时间、重连退避、执行/排队期限、取消宽限、队列/输入/缓存容量、上传重试与归档保留期等运行参数。
- 并发默认1不代表首版只支持串行；应能在实际宿主容量和管理员额度内配置多任务，任务间状态独立。
- 部署引导、代理基础设施、工作区/项目策略、客户端项目业务参数分别配置；接口认证与环境仍在客户端项目内，不因此搬到Web后台。
- 默认值与最大额度分开，显示继承来源、实际值、配置版本和生效方式；下级不能越过上级权限/上限，在途任务不能被静默改值。
- 可配置不表示可关闭正确鉴权、完整性和已有输出边界，也不启用尚未实现或无限期延期的能力。

## 7. 2026-10-26：现有Core脚本复用与混合进程策略

用户在讨论代理前后置脚本、单请求/多节点工作流的进程数，以及无脚本调试复用后明确要求：“可以，采用这个混合策略，更新并归档F7b整阶段实施计划。”本次已确认方向如下，替代原草案对应限制：

| 对象 | 已确认方向 |
| --- | --- |
| 真正无脚本的单请求调试 | 复用一个独立常驻调试子进程，按需创建、可有界并发、空闲回收；不在代理主进程执行 |
| 带脚本调试 | 一个完整任务一个独占子进程，复用现有Core同步脚本引擎/pm API，不每个前后置脚本另开进程 |
| 测试计划/套件、工作流 | 无论是否含脚本均按完整任务独占；循环、子流程、onError/finally不按节点拆进程 |
| 并发 | 共享在途调用与独占任务及其准备预留竞争同一代理总槽；局部共享上限不是额外额度，排队不开进程 |
| Core一致性 | 本机与代理、代理两条路径使用同一Core/宿主准备/脚本语义；固定输入、构建与实际运行档位，不发展第二套内核 |
| 取消与故障 | 普通取消只作用本调用；共享worker故障可能影响全部在途调用，如实逐项标记，不自动重发，确认旧代退出后才重建 |
| 可配置 | 总槽、共享在途上限/空闲期限、脚本模式/时限、子进程启动/监督及资源参数列入配套清单；默认建议不是容量保证 |

实施边界按R1计划落实：只支持受信内部同步测试脚本；节点启用与项目批准同时成立，优先单脚本/单版本，可显式整项目信任并醒目提示。批准绑定实际依赖与快照，修改失效/撤销阻止新启动；导入分享不自带授权。共享worker不装引擎，依赖检查含祖先/分支，不能靠删除脚本或关键词扫描取得资格。
