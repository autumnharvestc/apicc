# apicc 插件 API 与测试脚本安全设计规格

> 状态：已逐项确认，待书面审查
>
> 日期：2026-09-27
>
> 目标：建立可演进的插件公开契约，并把脚本严格限定为可授权、可审计、可复现的测试辅助能力。

## 1. 背景

apicc 当前插件定义仅包含 `name`、`version` 和 `setup(ctx)`，插件直接引用 `@apicc/core` 类型；加载器只检查对象形状，无法判断插件与宿主 API 是否兼容。同类贡献使用普通字符串作为键，重复项可能静默覆盖。插件通过 Node.js 动态导入进入宿主进程，因此本质上是拥有当前用户权限的受信代码。

当前测试脚本由 `node:vm` 执行，只注入 `pm` 对象并设置超时。该机制适合约束受信代码的可见上下文，但不是面对恶意代码的安全边界。随着共享项目、服务端任务、场景编排和压测进入产品范围，脚本必须具备明确的信任、权限、密钥、网络、资源和审计模型。

本规格同时落实以下已确认的产品决策：

1. 本地版完整提供设计、调试、Mock、测试、编排、压测和报告，不以登录或在线服务作为核心能力前置条件；
2. apicc 结构化契约是唯一事实来源，其他格式用于导入导出兼容；
3. 产品尚未发布，新契约不需要兼容旧 `ApiDefinition`；
4. 桌面任务由桌面进程执行，服务端任务由服务端独立执行，两者不强制互相迁移；
5. 压测先定位为可信的开发阶段压测，分布式性能平台留作未来扩展；
6. 团队、分享和共享历史等在线能力不能反向限制本地核心能力。

## 2. 设计原则

1. **公开契约与内部实现分离**：插件依赖稳定 SDK，不依赖 `@apicc/core` 内部模型。
2. **版本含义单一**：插件发布版本、插件 API 版本和宿主兼容范围分别表达。
3. **插件显式信任**：V1 插件是用户主动安装的本地受信代码，不伪装成沙箱。
4. **脚本最小能力**：脚本服务于测试，不是通用系统自动化环境。
5. **声明式优先**：常见提取、断言、编码、签名和数据操作优先使用可验证的内建操作。
6. **密钥不可读取优先**：共享和服务端脚本通过句柄使用密钥，不获得密钥原文。
7. **安全权限不可继承扩大**：子级脚本只能使用上级允许能力的交集。
8. **结果可解释**：脚本、请求、断言、清理和负载生成器错误分别报告。
9. **功能与压测同安全模型、不同执行配置**：压测不能为性能绕过权限，但必须避免脚本机制污染测量结果。

## 3. 插件 API V1

### 3.1 独立 SDK

新增稳定公开包 `@apicc/plugin-sdk`。插件只能从 SDK 导入公开定义、DTO、辅助函数和契约测试工具，不再从 `@apicc/core` 导入内部类型。

SDK V1 至少公开：

- `definePlugin()`；
- 插件清单与兼容性类型；
- 各扩展点的 V1 契约；
- 只读或受控可变的稳定 DTO；
- 错误与诊断类型；
- 插件契约测试工具。

SDK 不公开工作区内部对象、存储实现、Pinia 状态、Electron IPC 或可任意变更的领域实体。

### 3.2 三种版本

插件定义必须区分：

```ts
definePlugin({
  name: "apicc-plugin-demo",
  version: "1.4.2",
  apiVersion: 1,
  engines: { apicc: ">=0.3 <0.6" },
  capabilities: ["importer", "reporter"],
  setup(ctx) {}
});
```

| 字段 | 含义 | 规则 |
|---|---|---|
| `version` | 插件自身发布版本 | 使用 SemVer，由插件作者维护 |
| `apiVersion` | 插件协议主版本 | 破坏性公开契约变化时递增 |
| `engines.apicc` | 已验证的 apicc 产品版本范围 | 加载前由宿主检查 |

同一 `apiVersion` 内只能增加可选字段、扩展枚举处理能力或增加新扩展点，不能改变既有字段语义。正式发布后，宿主原则上支持当前和前一个插件 API 主版本；发布前可直接建立 V1，不提供当前试验接口的适配层。

### 3.3 加载顺序

插件加载必须按以下顺序执行：

1. 定位用户主动登记的插件；
2. 读取元数据但不执行 `setup()`；
3. 校验插件形状、`apiVersion` 和 `engines.apicc`；
4. 校验声明的扩展能力；
5. 检查贡献 ID 冲突；
6. 展示诊断并拒绝不兼容插件；
7. 仅在全部检查通过后执行 `setup()`。

单个插件失败不得阻断其他插件和应用启动，但失败插件的任何贡献都不能部分生效。

### 3.4 贡献标识与冲突

所有贡献使用命名空间 ID，例如：

```text
vendor.plugin/assert.contains-schema
vendor.plugin/import.raml
vendor.plugin/report.custom-html
```

- 重复 ID 默认拒绝后加载的贡献，并报告插件、贡献类型和冲突来源；
- 禁止静默覆盖；
- 内建贡献使用保留命名空间；
- 插件显示名称可以本地化，但持久化引用只使用稳定 ID。

### 3.5 信任边界

V1 插件只支持用户级安装和登记：

- 不允许项目携带插件清单并在克隆、导入或打开时自动执行；
- 插件拥有本机代码权限，界面必须明确提示该事实；
- 受信插件可以扩展协议、认证、导入器、报告器等平台能力；
- 不受信扩展未来采用进程外协议，本规格不要求 V1 实现通用不受信插件市场。

声明式 `permissions` 不能把当前动态导入插件变成安全沙箱，因此 V1 不提供虚假的插件权限承诺。

### 3.6 插件验收要求

| ID | 需求 | 验收 |
|---|---|---|
| PLUG-001 | 插件只依赖 `@apicc/plugin-sdk` | 官方脚手架和示例不再导入 `@apicc/core` |
| PLUG-002 | 加载前检查三种版本 | 不兼容插件的 `setup()` 从未执行，诊断包含期望与实际版本 |
| PLUG-003 | 贡献 ID 不可静默覆盖 | 重复注册测试得到确定失败，原贡献保持不变 |
| PLUG-004 | 插件注册具备原子性 | `setup()` 中途失败后无残留贡献 |
| PLUG-005 | SDK 提供契约测试 | 插件作者可在包内验证清单、贡献形状和 DTO 行为 |
| PLUG-006 | 工作区不能自动加载插件 | 含恶意插件字段的导入项目不会触发代码执行 |

## 4. 脚本分类与归属

### 4.1 三类脚本

| 类型 | 存储 | 同步 | 可供服务端使用 | 默认信任 |
|---|---|---|---|---|
| 本地私人脚本 | 本机用户配置 | 否 | 否 | 当前用户创建，可视为受信 |
| 项目共享脚本 | 项目资产 | Git/服务端 | 是 | 默认不信任 |
| 服务端任务脚本 | 共享脚本的不可变快照 | 服务端 | 是 | 仅按任务授权执行 |

私人脚本不能成为共享用例、共享场景或服务端任务的隐含依赖。把私人脚本转为共享脚本必须显式创建共享资产并进入共享信任流程。

### 4.2 声明式操作优先

平台优先提供以下内建操作：

- 设置、删除和提取变量；
- JSONPath、XPath、Header、Cookie 和正则提取；
- 断言与响应校验；
- 延时、随机值、时间戳和 UUID；
- Base64、URL 编码、Hash、HMAC 和签名；
- 受控辅助请求；
- 用户选择的测试数据读取；
- 平台管理的测试产物写出。

JavaScript 只用于声明式操作无法合理表达的测试逻辑。

## 5. 脚本运行时边界

### 5.1 语言与 API

apicc 脚本支持标准 JavaScript 和受控 `pm.*` API，但明确不兼容 Node.js/npm 运行时：

- 不提供 `require`、任意动态 `import`、`process`、原生 `fetch`、Node 内置模块和 npm 包；
- 编码、密码学、网络、文件选择和产物输出通过 `pm.*` 提供；
- Postman 导入只兼容明确列出的常用 `pm` API 子集；
- 导入遇到不支持的 API 必须报告具体位置和替代建议，不能静默降级；
- 本地与服务端实现必须通过同一套脚本契约测试。

运行时通过接口抽象与产品逻辑解耦。具体受限 JavaScript 引擎可以在实施阶段选型，但不得继续把 `node:vm` 作为共享或服务端不可信代码的安全边界。

### 5.2 禁止的系统能力

所有脚本均禁止直接：

- 访问任意文件路径；
- 启动进程或线程；
- 读取系统环境变量；
- 加载本机模块或原生扩展；
- 调用未经过平台策略的网络接口；
- 遍历工作区或读取无关项目数据。

需要文件时，脚本只能使用用户明确选择的测试数据或平台分配的临时产物句柄。数据库、Git、命令行等能力通过独立受控操作或受信插件实现，不通过脚本绕过权限体系。

## 6. 信任与授权

### 6.1 默认单脚本、单版本授权

共享脚本首次执行时展示：

- 来源、代码和相对上次受信版本的差异；
- 所需变量、网络目标和密钥引用；
- 执行阶段和影响的请求范围；
- 内容哈希与权限集合。

用户可以选择“仅运行一次”或“信任当前版本”。授权绑定脚本内容哈希和权限集合。脚本内容或权限变化只使该脚本授权失效，不影响其他脚本。

仅修改名称、说明或不影响语义的格式不要求重新授权。

### 6.2 可选信任整个项目

用户可以选择信任整个项目，界面必须醒目说明风险。项目级信任允许现有权限范围内的普通脚本内容持续更新，但以下变化始终要求重新授权：

- 新增或扩大网络白名单；
- 新增密钥引用；
- 申请本地密钥原文读取；
- 申请文件、进程或系统环境能力；
- 从本地执行扩展到服务端执行；
- 新增外部代码依赖；
- 项目来源、仓库地址或签名身份变化。

单脚本和项目级信任均可随时撤销。打开、导入和同步项目不执行脚本，也不主动请求信任；只有实际运行相关请求、用例或任务时才进入授权流程。

## 7. 网络权限

- 脚本可以读写当前 API 请求，不需要额外网络授权；
- 额外请求只能通过 `pm.sendRequest()`；
- 目标主机必须位于项目网络白名单；
- 首次使用或扩大白名单时重新授权；
- 服务端任务的出口白名单由具备任务管理权限的用户配置；
- 重定向后的最终目标同样受白名单约束；
- DNS、IP 和代理处理必须防止通过重绑定或重定向绕过目标限制。

功能测试可以有限使用辅助请求。压测迭代脚本默认禁止隐藏辅助请求，业务辅助调用应建模为显式场景节点；`setup` 和 `teardown` 中的辅助请求单独统计，不计入被测业务吞吐量。

## 8. 密钥模型

### 8.1 存储与引用

- 项目契约、脚本和环境只保存 `secretRef`，不保存密钥值；
- 本地密钥使用操作系统凭据库；
- 服务端密钥使用服务端加密存储，并按项目、任务和引用授权；
- Git、同步、导出、分享和 AI 上下文不得包含密钥原文；
- 审计只记录使用了哪个密钥引用，不记录值。

### 8.2 句柄式使用

共享脚本和服务端脚本永远不能读取密钥原文，只能使用句柄式 API，例如：

```js
pm.secrets.attachHeader("API_TOKEN", {
  name: "Authorization",
  prefix: "Bearer "
});

const signature = pm.crypto.hmacSha256(
  { secretRef: "SIGNING_KEY" },
  payload
);
```

本地私人脚本可以申请临时读取密钥原文，但必须显式授权并展示风险。原文读取能力不能被共享、同步或服务端快照继承。

## 9. 日志、历史与分享

### 9.1 永不持久化的内容

密钥原文不得进入：

- 脚本控制台；
- 请求历史；
- 功能与压测报告；
- 实际请求视图；
- 错误堆栈；
- 服务端任务日志；
- 分享文档、项目导出和 AI 上下文。

脚本日志统一使用受控 `pm.log()`，经过敏感值标记、敏感 Header 规则和项目自定义字段规则处理。报告必须标明内容已遮罩。

### 9.2 报文留存策略

- 本地调试历史默认保存遮罩后的完整请求和响应，支持按天数、数量限制或关闭；
- 本地测试报告默认保存失败用例的遮罩后报文，成功用例默认保存摘要；
- 服务端任务默认只保存执行元数据、断言和失败摘要；
- 服务端完整报文由项目显式开启并设置保留期限；
- 分享与导出始终执行密钥和自定义敏感字段遮罩。

## 10. 权限与审计

团队模式保留三个独立权限点：

1. 编辑共享脚本；
2. 管理密钥及任务绑定；
3. 管理服务端任务。

项目所有者可以同时拥有全部权限，不强制职责分离或双人审批。平台不根据“生产”“测试”等用户自定义环境名称实施特殊安全策略，因为环境可以复制、改名或重建，无法形成真实安全边界。

服务端执行至少审计：

- 触发者和实际执行身份；
- 项目、环境引用和执行快照 ID；
- 脚本哈希与获批权限；
- 使用的密钥引用名称；
- 访问的网络目标；
- 开始、结束、停止原因和结果；
- 权限拒绝、越界与资源限制事件。

## 11. 执行生命周期与冲突规则

### 11.1 前置操作

```text
项目 → 模块 → 外层目录 → 内层目录 → API → 用例/场景节点
```

越接近当前请求的操作越晚执行，可以覆盖上层普通值。

### 11.2 后置与 finally

```text
用例/场景节点 → API → 内层目录 → 外层目录 → 模块 → 项目
```

`finally` 使用同样的由内向外顺序，并在请求、脚本或断言失败后尽力执行。

### 11.3 冲突规则

- 普通变量后写覆盖前写；
- Header、Query 和 Cookie 的覆盖或删除记录来源轨迹；
- 断言只追加，下层脚本不能静默删除上层断言；
- 网络、密钥和其他安全能力取各层授权交集，子级不能扩大；
- 报告显示最终生效值的来源，敏感值始终遮罩。

## 12. 失败语义

- 前置脚本失败：不发送请求，当前用例或节点失败；
- 后置脚本失败：保留响应，当前用例或节点失败；
- 权限拒绝、网络越界、超时、内存超限：按明确的脚本错误类型失败；
- 批量执行是否继续由 `fail-fast` 策略决定；
- `finally` 失败单独记录，不覆盖最初失败原因；
- 报告分别展示请求错误、脚本错误、断言失败和清理失败。

## 13. 服务端任务快照

- 创建服务端定时任务时生成不可变执行快照；
- 快照包含契约、用例、场景、脚本哈希、权限、环境引用和插件 API 版本；
- 项目修改不会静默改变既有任务；
- 用户通过“更新到当前项目版本”查看差异并更新快照；
- “始终使用最新版本”是醒目标记的显式高风险选项；
- 权限扩大时任务自动暂停并等待重新授权；
- 每份报告记录实际快照 ID。

服务端脚本运行在专用任务执行器中，不进入 Spring 主服务进程。执行器使用受限身份、网络白名单、资源配额和可强制终止的隔离单元。

## 14. 功能测试与压测资源策略

### 14.1 统一安全模型

功能测试与压测共享相同的脚本语言、权限、密钥和网络规则。宿主必须设置脚本无法绕过的时间、CPU、内存、日志、变量、数据、产物和辅助请求硬上限。

具体默认数值由实施阶段通过基准测试确定，项目只能在宿主允许范围内配置，不能取消硬上限。

### 14.2 不同执行配置

功能测试侧重调试：允许较长脚本时间、有限辅助请求和较完整的脱敏日志。

压测侧重低开销和指标可信：

- 压测开始时创建固定隔离 Worker 池，脚本预编译后复用，禁止每次请求创建进程；
- 不同虚拟用户的变量上下文隔离；
- 支持 `setup`、`vuSetup`、`iteration` 和 `teardown` 生命周期；
- 迭代脚本默认禁止隐藏辅助请求；
- 成功日志默认关闭或低比例采样，错误按类型聚合并保留有限样本；
- 分别统计 `scriptTime`、`requestTime` 和 `iterationTime`；
- HTTP 延迟分位数使用 `requestTime`，业务体验使用 `iterationTime`；
- 脚本错误、目标服务错误、断言失败和负载生成器饱和分别统计；
- 生成器资源不足时必须在报告中标记，不能把客户端瓶颈解释成服务端性能。

## 15. 脚本 API 最小范围

V1 `pm` API 应围绕测试任务设计：

| 模块 | 能力 |
|---|---|
| `pm.request` | 读取/受控修改当前请求 |
| `pm.response` | 读取当前响应和结构化解析 |
| `pm.variables` | 读取作用域变量、写运行时变量 |
| `pm.environment` | 读取普通环境变量，不读取系统环境 |
| `pm.assert` | 追加脚本断言 |
| `pm.extract` | 声明式提取辅助 |
| `pm.sendRequest` | 受白名单和配额控制的辅助请求 |
| `pm.secrets` | 句柄式绑定密钥，不返回共享/服务端密钥原文 |
| `pm.crypto` | 使用密钥句柄完成摘要与签名 |
| `pm.files` | 读取用户选择的数据、写平台管理产物 |
| `pm.log` | 结构化、限量、统一脱敏日志 |

任何新增 API 都必须回答：是否属于测试辅助、需要什么权限、如何审计、是否会泄露密钥、如何在本地与服务端保持一致。

## 16. 验收要求

| ID | 需求 | 验收 |
|---|---|---|
| SCRIPT-001 | 打开、导入、同步项目不执行脚本 | 恶意夹具在三种操作后无执行痕迹 |
| SCRIPT-002 | 单脚本版本授权可撤销 | 内容或权限变化使对应授权失效，其他脚本不受影响 |
| SCRIPT-003 | 项目信任不允许权限静默扩大 | 新网络目标或密钥引用触发重新授权 |
| SCRIPT-004 | 无原生系统能力 | 脚本无法访问文件、进程、系统环境或模块加载器 |
| SCRIPT-005 | 网络白名单不可绕过 | 直接、重定向和名称解析测试均不能访问未授权目标 |
| SCRIPT-006 | 共享/服务端脚本拿不到密钥原文 | 日志、异常、编码和辅助请求测试均无法提取值 |
| SCRIPT-007 | 敏感信息不落盘 | 历史、报告、日志、分享、导出和 AI 夹具扫描无密钥原文 |
| SCRIPT-008 | 生命周期顺序确定 | 多层操作夹具的执行轨迹与本规格顺序一致 |
| SCRIPT-009 | finally 不覆盖原始错误 | 请求和清理同时失败时，两类错误均保留且主因不变 |
| SCRIPT-010 | 服务端任务可复现 | 项目修改后旧快照结果和脚本哈希不变 |
| SCRIPT-011 | 本地与服务端语义一致 | 同一契约测试在两个运行时得到相同结果和错误类型 |
| SCRIPT-012 | 压测脚本不污染 HTTP 指标 | 人工增加脚本延时只影响 `scriptTime/iterationTime`，不影响 `requestTime` |
| SCRIPT-013 | 压测上下文隔离 | 并发虚拟用户变量、密钥句柄和日志样本互不串扰 |
| SCRIPT-014 | 资源限制可终止失控代码 | 死循环、内存膨胀、日志洪泛和请求洪泛均被限额终止并正确分类 |

## 17. 明确不做

V1 不包含：

- 工作区随项目自动安装或执行插件；
- 对不受信 Node/npm 插件的安全沙箱承诺；
- 脚本直接访问任意文件、进程、系统环境或 npm 包；
- 共享和服务端脚本读取密钥原文；
- 根据环境名称判断“生产环境”并强制双人审批；
- 通过放宽脚本权限提升压测性能；
- 分布式负载生成与跨节点脚本状态同步。

## 18. 后续实施拆分

本规格通过书面审查后，实施计划应拆为至少四个可独立验收的工作包：

1. `@apicc/plugin-sdk`、插件清单 V1、原子注册和冲突治理；
2. 脚本契约、声明式操作、受限运行时与本地信任存储；
3. 密钥句柄、网络策略、脱敏、历史与报告数据策略；
4. 服务端任务执行器、不可变快照和压测 Worker 池集成。

结构化接口契约模型是插件 DTO 与脚本请求/响应模型的前置依赖；执行可信度基线是压测脚本集成的前置依赖。实施计划必须显式表达依赖关系，不能把四个工作包当作无序并行功能。
