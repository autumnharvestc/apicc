# CI94 测试前提修复回执

CI94 对应 `5b7e3881939da5051b76c34f9d71f8566616d903`。远端 Linux 构建/各包测试（26 条命令）、Windows 打包冒烟（20 条命令，实际 helper 收束）及品牌门禁均通过；Java 2194 项中出现 1 个断言失败和 1 个错误。原日志保留在本机 `local/ci94-test.log`。

本次仅修改四份测试及本回执，保留生产代码、数据库唯一约束、候选替代/保留规则和原来的业务断言。

## 两个根因

**调度测试占用了未来真实序号。** `ExecutionJobsApiTest` 在共享的持久 H2 内存库中，将真实任务手工绑定到不存在的 occurrence 123。任务来源按设计永久保留；后续 `ScheduledRecoveryTest` 的真实自增序号到达 123 时，正确触发唯一约束。后台调度计时器在该 fixture 中已被替换，未发现序号重置或生产幂等缺口。新增真实关联断言后，旧准备方式立即产生 expected 1 / actual 0 的有效失败，无需等序号自然走到 123。

将同名 verify 接口用例迁到已有的真实调度 fixture，通过 occurrence 和原任务提交权威创建任务，再检查 409、queued、永久来源及所属 scope/subject/job/execution 关联；项目任务数与 outbox 均保持不变。移除虚构来源造数，不清除真实来源或放宽约束。

**额度测试依赖已过期候选尚未清理。** 上轮新候选使同来源旧候选过期后，四个既有额度用例仍靠同一来源的多份旧候选堆积空间，遗漏了清理后的准备条件。显式触发正常清理的决定性反例显示：候选 3→1，空间约 12→6 MiB，但目标检查仍 running、snapshot 仍在；失败发生在降额之前。不是已证明的在途快照提前释放。

四个同族方法改用不同来源、不同合成地址的候选，显式清理后确认保留数量、适用性和真实字节。继续验证降额后的实际取消/失败、快照释放、物理 held/retained 归零、仍超额时拒绝新任务、有限排队预留、计划暂停及后续健康项目。没有禁用清理、调大超时或改变产品策略。
