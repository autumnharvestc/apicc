# 完整本地 CI 覆盖门禁（按需执行）

日常默认采用本地定向验证、必要回归和 GitHub CI。本入口是按需执行的重量级完整本地门禁，不是每次推送的默认前置步骤；运行前必须取得用户对本次全量的明确确认，并说明范围、必要性和预计耗时。`scripts/test-all.ps1`、全工作区测试、Java 全套及等效拆分执行的全量也遵循此规则。提交、合并、推送或此前某次全量的授权，不自动授权本次全量或重跑。

## 日常验证如何对齐 CI

选用例前先对照 `.github/workflows/ci.yml` 与 `scripts/ci-stage.mjs`，记录本次改动影响哪个任务、生产依赖和旧入口。用例数量不代表覆盖了依赖边界；新增功能的测试通过后，仍需核对受影响的旧消费者。

| 变更或失败类别 | 必须核对的影响面 | 最小验证方向 |
| --- | --- | --- |
| 新增源码指纹输入或严格比较的生成文件 | Git 属性、原始检出字节、生成器检查 | 真实 Windows／LF Git 检出与对应生成器 `--check`；同主机检出不冒称两种原生系统编译 |
| 新增能力或修改本地化显示 | 真实管理 API 的有限能力集合、可见业务文字 | 核对完整集合及角色语义；按中英字面量验证对应表格单元格 |
| 修改 Spring 注入类型、公共基础设施或可替换依赖 | 所有该类型的生产注入点，以及 `@MockitoBean`、`@MockBean`、`@Primary` 和直接构造点 | 从实际旧替换入口和新功能各选代表；不能只跑新增模块的自有夹具，也不能为通过而把旧接口 mock 改成具体类 |
| 物理目录、进程、句柄或未确认收束的占用 | 实际物理身份、别名、并发初始化、资源仍占用时的清理顺序 | 在相关原生平台跑真实生命周期反例；Windows 单跑通过不能替代 Linux 文件系统行为 |
| 共享数据库归属、租约、时钟或配额 | 旧业务时钟替换、真实 DB 时间、既有调度／取消／保留消费者 | 先查替换方式再选命名回归，核对实际收束和迟到写入；配置、代次与额度保护继续成立 |

CI 提前失败时，后续任务或包测试属于“未执行／未证明通过”。修复前序阻断后，将本阶段改动中尚未执行到的包列入验证选择，说明选了哪些代表入口、剩余哪些仍依赖远端 CI。不能把脚本单测打印的模拟阶段命令或 `# [CI ...] passed` 当成实际完整阶段结果。

交付记录分开列出本地命名用例、必要旧入口、原生平台检查和远端 CI；保留命令、退出码、实际执行／按名排除数量、源码候选及未覆盖项。独审核对这份对应关系及原始结果，不能只依据“测试很多／新增用例全绿”认可覆盖。上述规则不授权本地全量，也不要求每次修改重跑全套。

CI90–CI92 暴露的选择问题包括：遗漏新增字节敏感文件的 LF 合同、旧能力／显示断言、共享依赖的旧接口替换入口，以及被前序失败挡住的 Linux 目录生命周期用例。修复记录应区分原有问题、新引入回归和本轮首次执行到的检查。

## 完整门禁的执行与证据

获得本次确认后，先集中处理同类问题与环境前提，完成审核、确认基本收敛并冻结候选，再运行本入口。失败后先回到定向诊断与验证；再次执行全量需要用户重新确认。

在 **已取得本次确认、已提交且干净** 的 Windows 工作区运行：

```powershell
pwsh -NoProfile -File scripts/pre-push-ci.ps1
```

前提：Node 22.19.0、pnpm 11.21.0、`JAVA_HOME` 指向 JDK 21；Docker Desktop 的 Linux engine 与 `docker compose` 可用。缺任一前提、命令非零退出或证据缺失均视为失败。

入口先校验工具版本、执行 `pnpm install --frozen-lockfile`，随后运行现有 `test-all.ps1` 和 Windows `dist:dir` / `smoke:dir`。Linux 阶段用当前已提交 HEAD 创建 git bundle，在独占 Docker volume 中分别干净检出，依次运行与 `.github/workflows/ci.yml` 同一 `scripts/ci-stage.mjs` 入口：包构建与测试、Java 组合测试、品牌门禁。Docker daemon 与测试容器共用 volume 的真实绝对挂载路径，供嵌套代理容器读取同一份本地夹具和临时夹具。随后 Windows 宿主用同一共享阶段入口构建三款 Linux 镜像并运行部署冒烟；部署脚本访问 Docker 发布在宿主 `127.0.0.1` 的端口。Actions 的 Windows 打包任务随工作流已配置的分支推送和 PR 触发，当前没有仅 `main` 的任务级条件；本地完整入口每次执行时也覆盖它。

每次运行在 `local/ci88-fix/pre-push-*/` 留下候选 bundle、每阶段完整日志、结构化 `receipt.json`，以及白名单复制的 Linux Maven XML、F7f 组合结果和压测诊断。部署 JSON 从宿主 `local/` 中按冒烟前后的路径差集辨认，只有本次新生成且 `passed=true` 的文件计入 receipt。即使阶段失败也先收集现有证据，再清理本次独占容器和 volume。最终只有所有阶段、必要证据、清理和再次核对的同一干净 HEAD 均成立，receipt 才标记通过。Windows 全量的鲜 Maven XML 由 `test-all.ps1` 留在其输出的 `local/full-gate/` 路径。

此门禁覆盖 CI 的可执行阶段，但本机 Docker Linux 镜像和 GitHub runner 仍可能有 OS 补丁、网络、缓存、配额与负载差异。CI 专属的 checkout、工具安装、缓存和失败产物上传仍由 Actions 执行。失败产物只上传允许的诊断 JSON；F7f 组合仅上传 `facts.json`、`cleanup.json`、`result.json`。
