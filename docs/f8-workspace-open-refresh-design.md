# F8 桌面启动复用与本地工作区刷新设计

**决策日期**　2026-11-16。用户确认先做启动复用、同目录去重、显式刷新和保存冲突保留草稿。「在新窗口打开」列入后续需求。基线为用户确认 CI108 通过的 `3190af4e`。

## 1. 现状与本批边界

- 桌面主进程装配一份活动本地会话。项目签能按本地根目录和完整项目定位复用，根目录现按路径字符串比较。在线项目签按服务器、工作区和项目定位维持原行为。[桌面装配](../apps/desktop/src/main/main.ts) · [项目签](../apps/desktop/src/renderer/src/stores/tabs.ts)
- 现有 `WsOpen` 会重新读取工作区，并进入测试、工作流、压测和 Mock 的切换清理链。渲染层已有的 `workspace.refresh()` 只刷新主进程内存中的目录树。用户需要专门的「从磁盘刷新」入口来获取外部变更。[IPC](../apps/desktop/src/main/ipc.ts) · [工作区 store](../apps/desktop/src/renderer/src/stores/workspace.ts)
- CI108 对应的 Windows 包在两套独立配置中同时打开过同一合成工作区。一个实例保存后，另一实例的旧快照写入被拒绝，重新读入后可保存。该试验覆盖本地工作区，没有覆盖同配置并发或双实例在线协作。现有 Core 在写入锁前后校验工作区版本，因此不同项目也可能遇到同一个工作区级冲突。原始日志位于本工作树 `local/f8-desktop-pages/probe-multi-instance.log`。[写入日志与版本检查](../packages/core/src/storage/writeJournal.ts)

本批保留既有项目签、正式接口、用例、环境、工作流及测试资产的保存和执行入口。继续使用现有工作区级版本校验和事务写入，沿用在线协作的服务端版本策略。本批范围为桌面启动、本地工作区与对应的保存反馈，工作区格式、CLI 及服务端接口沿用现有版本。

## 2. 启动和打开目录

| 操作 | 预期行为 |
| --- | --- |
| 同一配置目录下再次正常启动 | 现有主窗口恢复并获得焦点。启动请求早于窗口就绪时，等窗口可用再处理。保留页面、项目签、草稿、登录状态及在途工作。后发进程在初始化业务会话前结束。 |
| 显式使用独立配置目录启动 | 继续允许独立进程，兼容现有 `--user-data-dir` 用法和隔离验收方式。使用实际打包程序验证配置目录生效、进程可并存。用户级凭据、网络配置等已有共享规则沿用当前实现，独立配置不承诺完整环境隔离。 |
| 打开当前活动的本地目录 | 主进程确认是同一实际目录后复用已打开的会话。保留导航、视图和运行状态。同一项目继续激活已有项目签。重复打开的短路发生在目录重载、清理任务和清除调试上下文之前。 |
| 打开已成签但当前未活动的本地目录 | 通过现有切入流程激活对应上下文及项目签，沿用已有跨工作区切换保护。 |
| 打开不同的本地目录 | 走现有打开流程。复制工作区到新目录，即使复制了内部 ID，仍按新目录识别。取消选择、路径不可用和目标打开失败要保留原可用界面，并明确反馈。 |

主进程在现有路径和权限检查允许的范围内解析实际目录。大小写、分隔符、尾部斜线和可解析的目录别名按真实文件系统身份比较，避免全平台统一转小写。路径无法解析时按现有打开错误处理，保留 Core 的根目录校验。项目定位仍需包含工作区、分组和项目。启动恢复兼容旧项目签中保存的路径，只有实际目录和完整项目定位都一致时才归并；同名项目和不同物理目录保持独立。

从启动、主页目录选择或项目签发来的打开意图汇入同一处「定位目标 → 判断复用或打开 → 交给现有窗口」流程。只抽取当前会复用的目录身份和打开判断。未来「在新窗口打开」可以在解析目标后替换窗口路由，继续复用相同的目录解析和验证。本批不新增多窗口开关、每窗口会话表、工作区长期锁或只读窗口模式。[后续需求](backlog.md#desktop-future-001-在新窗口打开工作区)

## 3. 显式刷新与冲突恢复

本地工作区已打开时，主页工作区的 `⋯` 菜单提供「从磁盘刷新」。本地保存遇到版本过期时，在当前保存位置给出可操作反馈并提供同一个刷新动作。确认对话框和反馈复用现有组件，固定文案随中英文切换，说明会影响的工作区或资产。正常重选同一目录仅作定位，重复点击刷新可以合并为一次在途操作。

从磁盘刷新由主进程读入工作区，沿用 Core 的结构校验、写锁和恢复诊断。使用现有本地会话队列和作用域校验，提交同一快照的根目录、版本、模型和目录树。读取失败、临时写占用、恢复诊断或工作区身份已变化时，保留当前有效视图和草稿，给出明确原因。若磁盘工作区已被另一工作区替换，要求用户用正常打开流程进入。刷新与在途写入串行。影响同一工作区的运行或导入/同步应用正在进行时提示稍后重试，继续显示原运行状态。重复打开无需等待所选工作区的执行结束。

### 刷新后如何处理编辑内容

| 编辑状态 | 首版处理 |
| --- | --- |
| 没有草稿 | 更新到磁盘版本，并保留仍存在的当前项目签、选中接口和页面。目标已删除时明确提示并回到可用位置。 |
| 有草稿，该资产的磁盘内容仍与编辑基线一致 | 保留用户输入、待保存状态和精确定位。按已核对的磁盘版本更新该资产的保存前提，使其他项目或资产变更不会继续阻断本次保存。 |
| 有草稿，该资产或保存所依赖的结构已变更、被删除或无法可靠比对 | 保留草稿和原基线，说明具体目标及冲突原因，阻止该项直接写回。用户可返回查看草稿，也可显式选择「载入磁盘版本」并确认放弃该项草稿。磁盘已删除时，明确说明该项无法再保存。继续编辑其他已安全刷新的资产。 |
| 刷新后又有外部写入 | 保存仍按预期版本和现有写入锁检查，后来的冲突重新进入同一处理流程。 |

判断以现有读写单元的稳定定位和保存基线为准。正式接口、调试请求、用例、全局变量和参数、环境变量和模块基础 URL、工作流、数据集和套件至少纳入清点。用例以用例 ID 和范围区分，同名或同 ID 的其他项目、其他目录不会成为刷新对象。复用现有保存快照和编辑器可读字段，无法可靠判断的入口按草稿冲突处理。全局参数和环境的比较沿用现有写入规范化。环境两步保存只更新已确认步骤的基线，第二步失败时保留其草稿和反馈。工作区刷新不为旧资产自动补写、不自动重试保存，也不扩展到自动合并或跨重启草稿恢复。

IPC 区分版本过期、写入暂忙、只读/恢复问题和一般错误。版本过期回执只携带稳定原因和必要归属，面向用户的提示不展开请求正文、配置原文或原始 JSON。旧回执只影响它对应的工作区及编辑目标。在线冲突仍走已有界面，在线相关资产复用组件时保留既有语义。

## 4. 后续方案：本地多开保存与跨项目提示

**状态**　启动复用、同目录去重、显式磁盘刷新与冲突草稿保护已交付。本节对应协作保存接续的本地批。[基础实施计划](f8-workspace-open-refresh-plan.md) · [协作保存实施与验收计划](f8-collaboration-save-plan.md) · [在线协作保存与更新设计](f8-online-collaboration-save-design.md)

| 场景 | 确认的行为 |
| --- | --- |
| 甲乙打开同一实际目录，甲正在编辑 A，乙保存另一项目 B | 甲的客户端检测到变化后，在工作区入口轻提示「B 项目有更新 · 查看」。A 的草稿、选中项、展开和滚动位置保留。甲查看后可主动应用磁盘更新。 |
| 甲继续保存 A | 主进程读取磁盘最新版本。A 的目标资产与相关依赖仍符合编辑基线时，在当前磁盘版本上应用甲的改动，提交涉及的文件。界面显示 A 已保存，B 的待应用提示仍可查看。 |
| A 的目标或依赖也被修改、删除，或磁盘快照不完整 | 保留甲的草稿，提示具体目标与原因，交给用户处理。现有写入锁、版本校验和事务日志继续保护提交。 |
| 甲乙打开不同的实际目录 | 各自检查和显示本目录的更新。复制出的工作区即使带有相同 ID，也各自独立。 |

检查时机为窗口回到前台、点击保存，以及主动「从磁盘刷新」。提示在下次检查发现变化时出现，首版采用按需检查。只在已识别到具体项目时显示其名称；实际内容相同则静默。被检测到的可见增删和修改先提示，用户应用后才更新目录和相关内容。

本地先覆盖不同资产的安全提交。业务冲突判断可与在线方案复用，磁盘读取和提交仍由本地宿主负责。Git 或其他编辑器可能直接改文件，提交优先沿用 Core 的增量写入和版本校验；磁盘身份或一致性无法确认时保留草稿。同一资产内的字段合并在在线规则验证后再评估。[Core 写入日志](../packages/core/src/storage/writeJournal.ts) · [本地规范同步的增量提交](../apps/desktop/src/main/sync/local.ts)

后续验收用两个独立实例从同一基线打开合成工作区。乙保存 B 后，让甲保持在 A 并分别验证回前台、保存及主动刷新。核对 B 提示、A 一次保存、应用前后目录位置。另用复制目录和同一资产竞争验证提示归属与草稿保留。

### 与当前计划的衔接评估

当前计划的「从磁盘刷新」是用户显式应用新内容的入口。后续增加的前台检查和保存前读取用于发现变化或校验写入。保存成功时，界面只确认本次写入的资产，其他项目的更新继续待应用。现有保存后还会从主进程取树，因此接入后续方案时须回归这条路径，避免甲保存 A 后把 B 的目录变化一并显示出来。[工作区树刷新](../apps/desktop/src/renderer/src/stores/workspace.ts)

「刷新暂忙」继续约束需要替换当前上下文的显式刷新。同根有活动运行、导入或应用时，后续检查只在能安全读取时提供变化提示。写入沿用现有任务、根目录、待处理计划和版本保护。若其他项目改动同时改变了 A 使用的工作区共享变量或其他依赖，按实际受影响范围核对草稿与基线。

前一轮支持手动刷新后在新版本继续保存，后续扩展支持在一次保存内对互不影响的变更完成重读与提交。两者分批交付时共用目录身份、磁盘快照读取和草稿归属规则。将两者合批需要同步更新实施范围和「一次保存」的验收条件。
